# Third of a Percent

[![ci](https://github.com/JacoboPacheco/third-of-a-percent/actions/workflows/ci.yml/badge.svg)](https://github.com/JacoboPacheco/third-of-a-percent/actions/workflows/ci.yml)

A bounds check makes a C++ program stop if an index is out of range; libc++ hardening turns these checks on in the standard library. Google reported that this costs 0.30% on average across its services, a third of a percent. Measured one loop at a time, the same checks make some loops (reverse, stride-2, matrix multiply) take 2.8 to 8.0 times as long as the same loop without them, at the study's sizes (x86-64, one compiler version, data that fits in the CPU cache). This repository holds that measurement, the machine code that explains it, and one command that re-checks every number.

A measurement study, not a library or a tool to install, for C++ engineers and tech leads deciding whether to turn on libc++ hardening. **Start here: the live page, https://jacobopacheco.github.io/third-of-a-percent/** Switch the check off and on, then pick a loop to read its machine code.

Status: work in progress (Oct 2026). The measurements described here are the ones so far; the page, notes and results may still change. Code written by AI coding agents directed by the author.

## In three sentences

1. Google reported that turning on bounds checks in C++'s standard library cost its services 0.30% on average.
2. This study built algorithm kernels and real programs with the checks off and on, timed each pair 20 to 40 times per side in alternating order against an A/A control (a program timed against a copy of itself, to see the machine's own noise), and showed from the machine code that the checks were there.
3. The average hides a map. On clang 18, libc++ 18 and `-O2`, loops where the check stops the compiler from using SIMD (working on several array elements per instruction; reverse, stride-2, matrix multiply) took 2.8 to 8.0 times as long in cache at the study's sizes.

Loops that count upward (forward loops) kept SIMD and cost little on the AMD models once code placement is controlled. The Intel and Arm results, with what each verdict means, are under [Results by CPU model](#results-by-cpu-model).

## Check it yourself

The live page above needs nothing installed. The rest of this section is optional, for re-checking the numbers: clone this repository and run the check:

```
git clone https://github.com/JacoboPacheco/third-of-a-percent
cd third-of-a-percent
python scripts/check.py
```

Recomputes every interval and verdict from the raw timings and checks the page's data (Python 3, numpy; about 35 minutes on a CI runner and about 55 on one Windows laptop, single-run estimates not re-timed with the 95-job pool). The page check also needs `pip install playwright` and `playwright install chromium`; without the package it is skipped. To view the page from your clone instead of the live one: `python -m http.server 8000 --directory site`, then open http://localhost:8000.

To rerun the measurement itself, in your fork:

```
gh workflow run measure.yml
```

Reruns the measurement in your fork (enable Actions in the fork first; `gh run watch`, then `gh run download <id>`; the per-job files are the `results-<cpu>-jN` artifacts, the pooled result is `pooled`). The workflow takes one runner label per run: add `-f runner=ubuntu-24.04-arm` for the Arm column, and pool those runs apart from the x86-64 ones (`python harness/pool.py <out.json> <run folders>`; the other steps are in [arm64/README.md](arm64/README.md)).

## The question

Google wrote that "Hardening libc++ resulted in an average 0.30% performance impact" across its services ([Google Security Blog, Nov 15 2024](https://security.googleblog.com/2024/11/retrofitting-spatial-safety-to-hundreds.html)). Hardening makes C++'s standard library check every `vector[i]` against the vector's size.

This study timed loops and programs with checks off and on: a different measurement, so it neither confirms nor contradicts Google's average.

**Words used here.**
- **SIMD**: one instruction working on several array elements at once.
- **A/A control**: timing a program against a copy of itself, to see the machine's own noise.
- **NONE / FAST**: the same program built without checks (NONE) and with libc++'s FAST hardening mode (FAST).
- **Verdict**: the per-CPU-model reading, computed from written rules, one of three: **MAP** (costs uneven across loop shapes), small everywhere, or **INCONCLUSIVE** (cannot be called from the data: a mixed picture, too noisy, too few jobs or a failed control).
- **Placement**: the memory address where a loop's code starts; moving it can change speed.
- **Aligned**: every loop's code starts on a 64-byte boundary (`-falign-loops=64`), so differences in where a loop starts are removed from the comparison.
- **Forward sum, forward add**: `s += a[i]` and `c[i] = a[i] + b[i]`, indices counting up.
- **PGO**: profile-guided optimization: the compiler sees a sample run first and tunes to it.

## Results by CPU model

- Forward loops cost little on the AMD models once code placement is controlled (0.82x to 1.06x aligned, one AVX2 exception, 1.11x); below 1x the checked loop ran faster (cause inferred: loop layout). As compiled, the forward add cost about 1.6x on two of the three AMD models.
- Intel: in all 29 Intel jobs seen (three models; 15 are in the 95-job pool, 5 in earlier runs, 9 more in set C) the forward add at L1 cost 1.05x to 1.20x aligned, against 0.82x to 0.84x on the AMD models. The Xeon 8573C (7 jobs) has no verdict (INCONCLUSIVE under the written rules): its forward add costs a measured 1.06x, over the 2% forward limit. The Xeon 6973P-C (7 jobs) has a verdict (MAP) that is borderline: with 6 jobs it was INCONCLUSIVE, its stencil at L2 ending at 1.026, over the same limit, and the seventh job moved that end to 1.018; its forward add of 1.20x is left out as placement-sensitive. A third model, the Xeon 8370C, drew 1 job, too few to judge. See the [details](readme-parts/DETAILS.md).
- Arm (a separate column; the figures above are x86-64): on one Arm core type (Neoverse-N2, 30 jobs in 3 runs, the same compiler, flags and rules) reverse and stride-2 lose their NEON loops and cost 6.58x and 5.50x at L1 (all ratios here as compiled); matrix multiply keeps its NEON loop and still costs 1.55x at L1 (1.02x at L2); forward loops cost 1.000x to 1.007x at L1 (the add and the stencil are placement-sensitive and not judged), against an A/A floor of 0.009% that belongs to one L1 cell. The verdict is INCONCLUSIVE under the written rules, which stay as written: the forward add at L2, aligned, has an interval ending at 1.021, over the 1.02 limit by 0.0011, a margin inside the bootstrap's own seed noise (8 of 400 other seeds end at or above 1.02) in a cell where an identical binary is as noisy (A/A half-width 2.6%), so the data cannot separate INCONCLUSIVE from MAP there. See [arm64/README.md](arm64/README.md).
- Loops that lose SIMD are rare in the general libraries counted and not rare in the numeric projects (counted, not timed).

## What was found

Some loops lose SIMD when a check is added. A check can stop the program at any element, so the compiler may process several elements at once only if it can show the whole range is in bounds. For forward loops it can (the check moves to the tail); for the reverse and stride-2 loops clang 18 reports that it cannot determine the number of iterations, and for matrix multiply that vectorizing is not beneficial. Compile-only tests narrow the cause (nothing timed; run on Compiler Explorer's clang 18.1.0 release candidate, not the timed Ubuntu 18.1.3). On clang 18, of 29 loops compiled with FAST, all 16 with an iteration count for every exit in the compiler's analysis were vectorized and none of the 13 with an uncounted exit, and hoisting the one check the reverse loop keeps inside it makes it vectorize (observed; that the vectorizer needs the count is inferred from the LLVM source; [reverse and stride-2](investigate/vectorizer/reverse-stride2/README.md)). For matrix multiply the cost model prices each of the two checks at 14 units, so a width-4 vector iteration costs 45 against 44 for four scalar ones (observed; [matrix multiply](investigate/vectorizer/matmul/README.md)).

- **2.8x to 8.0x slower** in cache, at the study's sizes, for loops that lose SIMD (reverse, stride-2, matrix multiply on x86-64 with clang 18), on all four CPU models with a verdict (three AMD, and the Xeon 6973P-C, borderline); the Xeon 8573C (no verdict) lost the same loops, and the two Xeon models (7 jobs each) range 3.2x to 6.6x. This is the main run; other setups tested separately (`siblings/`) reached about 9.7x at L1. Losing SIMD is only part of the cost: on EPYC 7763 at L1 a build with vectorization switched off by hand takes 3.3x as long for reverse (7.6x with the checks on, as compiled), 2.6x for stride-2 (5.1x) and 1.6x for matrix multiply (3.2x). The rest is presumably the per-element compare and branch (inferred, not isolated).
- **1 of 593** vectorized loops in 19 general libraries lose SIMD, against 444 of 4,968 in 25 numeric projects. Counted, not timed. Of the 593, 443 are inside libc++'s own headers and none of those was lost; counting project code only, it is 1 of 150 against 444 of 1,609. In the numeric set 7 of 25 projects have any lost loop, and LightGBM holds 331 of the 444.
- **Real programs timed whole** (six workloads from four projects picked for their lost loops: LightGBM with three option sets, Draco, tiny-dnn, Spectra): detectably slower for five of the six on EPYC 7763 (1.2% to 7.5%, 16 jobs; three of the four projects), four on EPYC 9V74 (3 jobs), three on EPYC 9V45 (5 jobs); the rest were not detectable. Two control programs without lost loops (meshoptimizer, {fmt}) showed no detectable slowdown.
- **Code placement and PGO.** Across 4 placements the reverse loop stays at 5.2x to 8.0x and the forward sum near 1x; the forward add swings 0.82x to 1.60x on two models (as compiled 1.58x on EPYC 7763 and 1.60x on 9V74, traced to loop layout, not the check's own instructions), and the verdict leaves out the forward cells that depend on placement. PGO, trained on the timed input, left the cost in most rows.
- **0.99x to 1.09x** for the reverse loop after one added size check before it, with the checks still on.
- **GCC differs.** With GCC 14 and libstdc++'s own `_GLIBCXX_ASSERTIONS` (a different library, different checks) at `-O3`, even the forward add loses SIMD and runs 4.9x to 8.5x slower (7 jobs on 3 CPU models; the low end is one job).

## How much to trust it

- **Shared machines.** GitHub picks each job's CPU. The kernel pool is 95 jobs in 15 runs (23 to 29 jobs for each AMD model, 7 for each of the two main Xeon models, 1 for a third Xeon model); 65 of them come from twelve later runs. Ten of those runs dispatched 100 jobs and 45 returned results: all 100 finished their timing step, and the other 55 were cancelled at the 22-minute limit during the whole-repository check the workflow then ran, before the upload, and returned nothing (the workflow now uploads first). The cut fell unevenly by CPU model (EPYC 7763: 1 of the 45 that returned, against 19 of the first 30 jobs), and the effect of that mix on the ratios was not tested. Two more runs, dispatched with the limit raised to 45 minutes to check that jobs return (not chosen on their results), returned 20 of 20 jobs, 9 of them on EPYC 7763; every one ran past 22 minutes, which supports the account that the old limit, not the timing, cut the others.
- **Mostly x86-64.** Every figure outside the Arm bullet is x86-64 (AMD and Intel). The Arm column is one core type (Neoverse-N2) on shared machines, 30 jobs in 3 runs, clang 18 only; its verdict is INCONCLUSIVE (a borderline one, see the Arm bullet above), and nothing is said about Apple silicon, AWS Graviton or other Arm cores.
- **Mostly one toolchain.** Ubuntu clang 18, libc++, `-O2`, FAST mode. Clang and libc++ 19 to 21, timed on the eight loops (one CPU model with enough jobs), still lose the reverse and stride-2 loops; matrix multiply keeps SIMD there but is not free (1.6x at L1 on EPYC 7763, as slow as a build with no vectorization at all, and 1.15x at L2). A compile-only sweep (`ce-sweep/`, nothing timed) finds matrix multiply lost on clang 16 to 18 at baseline x86-64, kept on 19 to 22 (Ubuntu's own clang 20.1.2 and libc++ 20 agree), and lost again on clang 23.1 and trunk (as served on 2026-10-12). The change is in the compiler, not the library, and clang 19 to 21 price each of the two checks at 1 cost unit where clang 18 prices them at 14 (observed on Compiler Explorer's builds, not the timed ones); that LLVM commit `b6a8f5486b` caused it is inferred, not tested ([study](investigate/vectorizer/matmul/README.md)).
- **Machine state.** Over 10 jobs, steal was 0%, and reported CPU frequency drifted at most 0.57%. The driver was seen on the timed core's hyperthread sibling in 8 jobs.
- **Sizes.** The 2.8x to 8.0x is for the study's sizes. On EPYC 7763 the matrix-multiply sweep gives, as compiled, 2.5x at d = 12, 3.2x at d = 36 (the study's L1 size) and 4.2x at d = 76 (past its 32 KiB L1d), so 2.8x is not a floor for these loops.
- **Counts are not time.** The 593 and 4,968 are loops, not hotness.
- **Real programs** (four projects) were picked because they contain lost loops, not sampled.
- **Rules were loosened after seeing results.** The day-one test (the first two runs) judged forward loops by a rule that both runs failed, so the result was no-go as written; the rule was then relaxed in `harness/criteria.json`. The later versions (v2, v3) changed no threshold but added rules (the aligned column, the layout A/A, placement-sensitive cells, pooling per CPU model, 40 repetitions per side) after earlier results were known, so they are not pre-registered. Each rule file was committed before the runs it judges, and all versions are kept.
- **Independence and holdout.** On the 95-job pool a block bootstrap and the other interval methods tried (exploratory, [report](robustness/report.md)) change no verdict form on EPYC 7763, 9V74, 9V45 or the Xeon 8573C; the Xeon 6973P-C stays MAP under seven of the eight, and changes with the set of jobs more than with the method (leaving one job out, in turn, gives INCONCLUSIVE in 6 of its 7 cases). A fresh, pre-planned run matched the original 30-job pool on EPYC 7763 and 9V74, not 9V45. Intervals still understate run-to-run spread: on EPYC 7763 a run's point fell outside another run's interval in 168 of 640 comparisons (26%; 17% in the 75-job pool).

## Replication and the matrix-multiply sweep

Two verdicts rested on a thin margin, so two replication sets were planned in [replication/PLAN.md](replication/PLAN.md) before they were dispatched (the order rests on a commit time in the author's unpublished development history, 27 seconds before the first job's recorded start; no public record shows it, and the plan's hash in `replication/results.json` is computed when the comparison is built, so it shows the file is unchanged, not when it was written): set B, 30 more Arm jobs in 3 runs (29 on Neoverse-N2 and 1 on a Neoverse-V3 core, which has no verdict), and set C, 40 more x86-64 jobs in 4 runs, both dispatched from the default branch at commit 32ab03c. Each set is pooled alone, with the same code and the unchanged rules, and reported beside the pool it replicates; the verdicts and numbers above stay as they were. The pooled forms of the earlier jobs with the new ones are secondary, because the sets were requested after a borderline reading. Two of the four set-C combine jobs ended red on `harness/pool_check.py`, on a model with fewer than 3 jobs (one job in one run, two in the other); the checker now samples only models with 3 or more jobs (the minimum for a verdict), no verdict uses a model with fewer, and the pooled files and the rules are unchanged: only that check's sampling rule changed.

- **Arm.** Set B alone (29 Neoverse-N2 jobs) is INCONCLUSIVE again, on the same cell: the forward add at L2, aligned, ends at 1.0211 in set A and 1.0247 in set B against the 1.02 limit, with a point estimate below 1 in both (0.986 and 0.995). The cell sits close to the 1.02 limit in both sets, so a second INCONCLUSIVE is a weak repeat of the word and not strong evidence for it. Sets A and B pooled (59 Neoverse-N2 jobs) give MAP, with that end at 1.0150; the harness labels that form unstable, because each of the six runs alone is INCONCLUSIVE. The stored Arm verdict stays INCONCLUSIVE.
- **x86-64.** Four models had 3 or more jobs in set C. Two gave the same verdict word as the 95-job pool (EPYC 7763 and 9V74, MAP) and two a different one. On EPYC 9V45 (23 jobs MAP, then 5 jobs INCONCLUSIVE) the stencil at L1 is left out as placement-sensitive in the 95-job pool and judged in set C; its aligned upper end is 1.0204 and 1.0202 against the 1.02 limit. On the Xeon 8573C (7 jobs INCONCLUSIVE, then 7 jobs MAP) the forward add at L1 is judged in the 95-job pool and left out in set C; it costs 1.058 and 1.060 aligned. In both, the word changed because the written rule treated one cell differently, while the measured cost of the cell is about the same. The 8573C's MAP in set C is not the cost going away: the exempt forward add still costs 1.054 as compiled and 1.060 aligned.
- **Not tested.** Set C drew 1 job of the Xeon 6973P-C (3 are the minimum), so the question of its borderline MAP has no answer from these sets. Pooled with its 7 earlier jobs (8 jobs, a secondary form) it is INCONCLUSIVE, because the stencil at L1, left out as placement-sensitive in the 7-job pool, is judged and ends at 1.0216; one added job does not settle which word is right.
- **Reproduction and the headline.** 26 of 32 Arm points and 101 of 128 x86-64 points lie inside the earlier pool's interval, counting the as-compiled and the aligned column (aligned alone: 11 of 16 and 48 of 64, the form the plan asked for; the both-column count was chosen after the data were in); 30 of 32 and 122 of 128 differ from the earlier point by under 1%, and the largest differences are 3.74% (Arm stride-2 at L2, aligned) and 2.14% (Xeon 8573C stride-2 at L2, as compiled). The inside test is strict where the earlier interval is very narrow (a half-width under 0.1% of the ratio for 18 of the 32 Arm points and 24 of the 128 x86-64 points); the farthest missed point is 0.67% (Arm) and 0.73% (x86-64) from the interval. The count is descriptive: a new pooled point carries its own noise, so fewer than 95% of points are expected inside even when nothing has changed. For reverse, stride-2 and matrix multiply in cache, set C ranges from 2.805x to 7.993x over the four models with 3 or more jobs, so the printed 2.8x to 8.0x stands; one cell, the EPYC 9V45 stride-2 at L1 as compiled (5 jobs, 2.8053x), lies 0.0003x under the stored minimum of 2.8055x and prints as 2.8x.

The Arm matrix-multiply cost (1.55x at L1 with the NEON loop kept) rested on a reading of the listing. [dsweep/PLAN.md](dsweep/PLAN.md) fixed a test before any run. It was drafted before the sweep code, revised while the code was written and once more after a review that changed the deciding statistic, and committed alone, before the code commit and the first run, in the author's unpublished development history; its hash, stored in every result file, shows that it did not change after the runs, and the order before the runs cannot be checked from public records. The test: is the time FAST adds per inner call a fixed cost (H1), proportional to the matrix size (H2), or smaller at larger sizes ("falls")? Three runs (18 jobs: 6 on Arm in one run, 12 on x86-64 in two) timed matrix multiply at 15 to 17 sizes for each CPU model.

- **Registered words.** EPYC 7763 (9 jobs, 2 runs): H2, a cost per element, which the plan expected where the loop loses SIMD. Neoverse-N2 (6 jobs, 1 run): "neither", because the two columns disagree: as compiled the excess "falls" (fixed share 1.332), aligned it is H1 (1.090). Both shares are above 1, so it is not a mixture. EPYC 9V45 (2 jobs) and Xeon 8573C (1 job) were too few for a word. The plan's illustrative table gave R(12) = 3.35 under H1 and 2.31 was observed, so the table's size did not hold; the rule decides, not the table.
- **What the numbers show without the word.** On Arm H2 is rejected in both columns. FAST adds 77 extra instructions per inner call (77.0 to 77.2) at every size with d = 4 mod 8 from 12 to 148 (instruction counts, a secondary column, not times). As compiled, the excess time per inner call is 4.9 ns at d = 12, 3.8 to 4.0 ns at d = 28, 36, 44, 52, 76 and 108, 2.8 ns at d = 148 and 0.46 ns at d = 209; aligned, 4.7 ns, 4.2 to 4.3 ns, 3.7 ns and 0.50 ns. The word "falls" as compiled rests on the two smallest sizes, 12 and 20, with the excess flat, at the sizes with d = 4 mod 8, from d = 28 to d = 108, across the L1 boundary of the core (d = 76 and 108 are past its 64 KiB L1d), and smaller again only at d = 148 and d = 209, which are context and not fitted (a reading made after the result, not part of the rule). A setup cost before the NEON loop is consistent with this; the registered word is still "neither", and no further runs will be made.
- **Caveats.** Arm is one run of six near-identical jobs, so its intervals cannot show run-to-run or host-to-host spread; `-falign-loops=64` moves every loop on Arm (16 of the 17 sizes are flagged placement-sensitive), so the aligned column is not a pure placement control; no hardware counters were read. In the residue scan (context, not fitted), d = 48, a multiple of 8, costs 2.63x as compiled against 1.50x and 1.62x at 49 and 47, so the 1.55x belongs to the study size, which is 4 mod 8.

## Where things are

Start with `kernels/` and `site/`; the rest is evidence.

- **Study:** `kernels/` the 8 loops; `programs/` the two small programs (json, fmt) timed in the early runs; `realworld/` the real programs timed whole; `corpus/` the loop census; `harness/` times and judges; `mitigate/` the rewrite that restores SIMD.
- **Runs:** `results/` every run as downloaded (the kernel pool is `s7-pooled`: the 30 jobs of `s4-run-*`, also pooled alone in `s4-pooled`, plus the 45 of `s6-run-*` and the 20 of `s7-run-*`; `s6-pooled` is the 75-job pool before the last two runs; the Arm column is the 30 jobs of `s8-arm-run-*`, pooled apart in `s8-arm-pooled`); `arm64/`, `layout-sweep/`, `pgo/`, `versions/`, `environment/`, `robustness/` the follow-up columns, each with its own README or plan; `siblings/` and `ce-sweep/` other compilers and modes; `variants/` a compile-only test of other loop spellings; `replication/` the plan for the two replication sets (committed before they were dispatched, in unpublished history), the script that compares them with the pools they replicate and its `results.json` (runs `s9-arm-run-*` and `s9-run-*`, pooled in `s9-*-pooled`); `dsweep/` the matrix-multiply sweep: its plan (committed alone before the code and any run, in unpublished history, and unchanged since), code and workflow (runs `s10-dsweep-run-*`, pooled in `s10-dsweep-pooled`), dispatched from the temporary public branch `dsweep-smoke` (commit 8c874ec), where the d-sweep workflow is the file `ci.yml` (only a workflow already on the default branch can be dispatched); the branch is kept because the run records name that commit.
- **Evidence and review:** `dayone/` the first test, its rules and raw data; `claims-audit/` dated reports from separate checks of the page figures (some of the scripts are not published); `audit/` a separate audit of the S3 run; `investigate/` why the forward add cost 1.6x and, in `vectorizer/`, why the reverse, stride-2 and matrix-multiply loops lose SIMD (compile-only); `docs/` the day-one result; `gaps/` the related-work table (sources read); `tools/` the `lostloops` tool that lists which loops lose SIMD.
