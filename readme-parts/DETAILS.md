# Third of a Percent: the details

The long version behind the [README](../README.md): the full method, every finding with its per-CPU numbers, the limits and the stage history.

## The claim, the method and the findings

**The claim.** In November 2024 Google wrote: "Hardening libc++ resulted in an average 0.30% performance impact across our services" ([Google Security Blog, Nov 15 2024](https://security.googleblog.com/2024/11/retrofitting-spatial-safety-to-hundreds.html)). Hardening means libc++, the C++ standard library that ships with clang, checks, among other things, every `vector[i]` against the vector's size and stops the program on an out-of-range index.

**What this project did.** It built 8 small loops written for the test (forward, two-array, stencil, reverse, stride-2, gather, histogram, matrix multiply) twice, once with the checks off (NONE) and once with libc++'s FAST hardening mode on, and timed each pair in alternating order on GitHub's shared runners: 95 jobs over 15 runs (the original 30 jobs in 3 runs, then 45 more from ten later runs and 20 more from two further runs), 40 repetitions per side, pooled per CPU model with an interval that includes the spread between jobs, against a control that times one binary against a byte-identical copy of itself. The compiler's own remarks and the assembly show where each check landed. Then it asked four follow-up questions: how often real code has the loops that pay (a census of 44 open-source projects), how to keep the checks and not pay (rewrites), whether other toolchains behave the same (GCC 14, clang 20, the other libc++ modes, AVX2), and why one forward loop looked expensive (the loop layout the check induces).

**What it found: a map, not one number.**

- **Loops that lose SIMD under the check pay several times over.** Reverse, stride-2 and (under clang 18) matrix multiply are vectorized with the checks off and not vectorized with them on, so they run one element at a time. In cache they ran **2.8x to 8.0x slower** on every CPU model drawn (pooled over runs, `results/s7-pooled/pooled.json`). The compiler's reason differs: for the reverse and stride-2 loops it reports that it cannot determine the number of iterations; for matrix multiply it reports that vectorization is not beneficial (a cost-model remark). Compile-only studies on Compiler Explorer (nothing timed; its clang 18.1.0 is a release-candidate build, not the Ubuntu 18.1.3 that was timed; each statement is labelled observed, inferred or not established in the folder) say more:
  - **Reverse and stride-2** ([investigate/vectorizer/reverse-stride2](../investigate/vectorizer/reverse-stride2/README.md), 72 saved answers). Observed: each FAST check is a branch to a trap, so an extra exit of the loop; over 29 loops compiled with FAST on clang 18.1.0, a loop was vectorized exactly when the compiler's analysis (ScalarEvolution) had an iteration count for every exit (16 of 16 loops with a count for every exit vectorized, none of the 13 with an uncounted exit); in hand-written IR that changes only the expression of one stride-2 bound, the vectorizer vectorized exactly the 8 of 14 functions whose exit got a count. In the reverse loop the one check left inside the loop is a loop-invariant branch, and adding one loop-unswitching pass before the vectorizer (on the saved IR and in `opt` 18.1.0's full -O2 pipeline) vectorizes it; the stride-2 loop does not change. Inferred from knowledge of the LLVM source, not observed: that the vectorizer requires the count, and the rule that gives the stride-2 checks none. Clang 19 prints the same message; clang 20, 21 and trunk (as served on 2026-10-16) print early-exit wording, and the two loops are still not vectorized (observed). The timed Ubuntu 18.1.3 printed the same "could not determine number of loop iterations" remark for both loops (`dayone/results/run-38116223923/remarks.k04_rev.fast.txt` and `remarks.k05_stride2.fast.txt`); the rest of the quoted output was not compared with the timed build.
  - **Matrix multiply** ([investigate/vectorizer/matmul](../investigate/vectorizer/matmul/README.md), 94 compile requests, all answered and saved). Observed on clang 18.1.0 at baseline x86-64 (SSE2): legality passes, and the cost model prices each of the two bounds-check compares at 14 units at width 4 (6 on SSE4.2, 3 on AVX2, where clang 18 vectorizes the loop), so the width-4 loop sums to 45 against 44 for four scalar iterations and the vectorizer logs that vectorizing is not beneficial. Inferred: that this one unit decides, and that the price is high because SSE2 has no 64-bit vector compare. Clang 19 to 21 find the two compares uniform and price them at 1 each (observed).

  Turning vectorization off by hand costs matrix multiply 1.6x at L1 and 1.7x at L2 against 3.2x and 3.8x with the checks on (EPYC 7763, `results/s3-run-38121166129/`: its two 7763 jobs agree; the 29-job pool in `results/s7-pooled/pooled.json` gives 1.63x and 1.75x), so only part of its clang 18 cost is the lost SIMD. The same holds for the other two lost loops. Pooled EPYC 7763 positive control (29 jobs, build with `-fno-vectorize` against NONE, as compiled; `positive` in `results/s7-pooled/pooled.json`), against FAST over NONE in the same column: reverse 3.28x at L1 and 3.50x at L2 against 7.61x and 7.68x; stride-2 2.58x and 2.86x against 5.08x and 5.01x; matrix multiply 1.63x and 1.75x against 3.19x and 3.79x. On that model the build with vectorization switched off by hand accounts for part of the cost of each lost loop and not all of it. The remainder is presumably the per-element compare and branch the check adds to a loop that now runs one element at a time; that is an inference, not isolated by any control. The same comparison on the other CPU models has the no-vectorize build at 1.5x to 3.4x at L1 against 2.8x to 6.6x with the checks on (EPYC 9V45, EPYC 9V74, Xeon 8573C and Xeon 6973P-C).
- **Forward loops pay little under clang on the AMD models.** With every hot loop aligned to 64 bytes, forward loops ran 0.82x to 1.06x of the unchecked time there; both ends are cells the verdict leaves out as placement-sensitive, and the forward cells it judges ran 0.999x to 1.002x. The Intel models differ. In each of 20 Intel jobs seen (three models, 15 of them in the kernel pool) the forward add at L1, aligned, cost 1.05x to 1.20x: Xeon 8370C 1.05x to 1.06x (4 jobs, 1 in the kernel pool), Xeon 8573C 1.05x to 1.08x (9 jobs; the 7 pooled ones 1.052 to 1.068, pooled 1.058 [1.053, 1.064]) and Xeon 6973P-C 1.19x to 1.20x (7 jobs, 1.194 to 1.203, pooled 1.199 [1.188, 1.204]). These figures are for the main toolchain; with `-march=x86-64-v3` the forward add reached 1.11x on one EPYC 9V45 job (`siblings/`).
- **The 1.6x forward add was the loop layout, not the check's instructions.** As compiled, `k02_add_fwd` ran about 1.6x slower on EPYC 7763 and 9V74. The check's own instructions were not the cause; the loop layout the check induces was: with the check, clang emits a shorter loop that handles 4 numbers per pass instead of 8, and as placed it runs slower on these CPUs, while aligned it runs at 0.82x to 0.84x. The hardware mechanism is inferred, since these VMs have no cycle counters ([investigate/FINDINGS.md](../investigate/FINDINGS.md)).
- **The verdict holds per CPU model, not as one number for the page:**

  On the AMD rows, both ends of the forward column are placement-sensitive cells, which the verdict leaves out. On the Xeon 8573C row no headline number is printed. For the Xeon 8573C the forward add is not placement-sensitive, so the verdict counts it and it fails the rule (point 1.058, limit 1.02). For the Xeon 6973P-C the forward add at L1 (aligned 1.199, as compiled 1.231) is placement-sensitive and left out, and the verdict passes on the stencil at L2, whose interval ends at 1.018, a margin of 0.0016 under the limit. With the 6 jobs of the 75-job pool the same cell ended at 1.026 and the model was INCONCLUSIVE. The seventh job came from a noisy machine (its own A/A control 2.2%, above the 2% limit for a single job's own verdict, and a stencil ratio of 0.972, the lowest of the seven) and moved the end under the limit; the pooled rules exclude no job on its own A/A control (`harness/criteria-v3.json`). Pooling the seven jobs again with each one left out in turn gives INCONCLUSIVE in 6 of the 7 cases (MAP only without job 5 of run 38831094582; `tests/test_readme_numbers.py` repeats this), and the model is MAP under 7 of the 8 interval methods of the robustness analysis (INCONCLUSIVE only under the first form of the lag-1 correction). The form depends on which jobs were drawn more than on the interval method, and the verdict is borderline. Neither Xeon model has a run with 3 jobs, so stability is not assessable, and the jobs of each came from 6 runs (at most 2 per run). The Xeon Platinum 8370C drew 1 job (3 are needed): no verdict and no numbers shown.

- **Instruction counts are not time.** Cachegrind counts the same extra instructions on every CPU (reverse 7.9x to 8.0x, stride-2 5.1x to 5.2x, gather 2.7x), but the time cost differs by CPU: stride-2 costs 2.8x to 3.0x on EPYC 9V45 and 5.1x to 5.2x on EPYC 9V74. `k02_add_fwd` runs 1.26x to 1.29x more instructions and, on the AMD models, is no slower aligned (0.82x to 1.00x); on the Intel models it is 1.06x at L1 on the Xeon 8573C and 1.20x on the Xeon 6973P-C (7 pooled jobs each).
- **In real code, these loops are rare in general libraries and not rare in numeric code** (a count of loops from the compiler's own records, nothing timed; [corpus/README.md](../corpus/README.md)). In 19 libraries (parsers, JSON/YAML/XML, compression, logging and a few others): 1 of 593 vectorized loops lost under FAST. In 25 numeric, physics, graphics, machine-learning and compression projects (including Stockfish and EnTT), listed before compiling ([corpus/PLAN2.md](../corpus/PLAN2.md)): 444 of 4,968 lost, at 77 of 654 distinct source locations. 331 of the 444 are in LightGBM (without it, 113 of 2,415), and 18 of the 25 projects lose none.
- **What to change** (measured on 4 kernels; [mitigate/README.md](../mitigate/README.md)):
  - Reverse loop: one up-front size check, or a `std::span` taken once with `first(n)`, brings back SIMD with hardening still on: 1.00x on EPYC 7763 and 9V74, 1.06x to 1.09x on 9V45.
  - Matrix multiply: raw row pointers behind one up-front size check: 0.99x to 1.00x. Row spans keep every access checked and cost 1.09x to 1.37x at L1.
  - Stride-2: a span plus `#pragma clang loop interleave_count(2)`, 0.96x to 1.03x. A size check alone changes nothing.
  - A trap: `std::transform` over `rbegin()`/`rend()` is fast, but silently unsafe, because libc++ 18 does not check vector iterators in FAST mode.
- **Other toolchains differ** ([siblings/README.md](../siblings/README.md)). clang 20 and libc++'s EXTENSIVE and DEBUG modes draw the same line for forward, reverse and stride-2 loops (clang 20, and AVX2, keep matrix multiply vectorized; it still costs 1.5x to 2.3x at L1). GCC 14 with `_GLIBCXX_ASSERTIONS` does not: at `-O3` its checks stop the forward add and the stencil from vectorizing too (forward add 4.9x to 8.5x; the forward sum stays vectorized), and at `-O2`, where nothing vectorizes, they still cost up to 2.2x (2.4x for the gather, one job).
- **Newer clang and libc++, timed** (`versions/`, run 38471430657). Clang and libc++ 19.1.7, 20.1.8 and 21.1.8 from apt.llvm.org, the same harness and eight loops, 30 jobs in one run. The reverse and stride-2 loops lose SIMD under FAST on every toolchain and CPU model that ran: reverse 3.1x to 8.0x and stride-2 2.8x to 5.3x over all rows; on EPYC 7763, the one model with 3 or more jobs on each toolchain (6, 5 and 4), reverse 4.7x to 8.0x (4.7x to 4.8x under clang 21) and stride-2 4.9x to 5.1x. Matrix multiply is vectorized in both builds on all three and costs 1.61x at L1 and 1.15x at L2 on EPYC 7763 (under clang 18 it is lost, at 3.2x to 4.8x across the five CPU models: 3.2x at L1 and 3.8x at L2 on EPYC 7763, up to 4.8x on EPYC 9V45 as compiled), so the loss of SIMD seen on clang 18 does not hold there; at L1 the checked clang 19 build is about as slow as one with vectorization switched off by hand (1.61x against 1.62x, same job). Whether matrix multiply is lost depends on the clang version: a compile-only sweep on Compiler Explorer (`ce-sweep/`, nothing timed) finds it lost on clang 16 to 18 at baseline x86-64, kept on 19 to 22, and lost again on clang 23.1 and trunk (as served on 2026-10-12; clang 22, 23.1 and trunk were not timed). The forward add's 1.6x as-compiled cost on EPYC 7763 under clang 18 is not seen (1.01x). Every toolchain's form is INCONCLUSIVE under the written rule (`versions/PLAN.md`, committed before the run): matrix multiply misses the forward limit, and the other CPU models drew 1 or 2 jobs. One run, so no run-to-run check. Ubuntu's own clang 20.1.2 with libc++ 20 (`siblings/`) also keeps matrix multiply vectorized, so a difference in where the toolchain came from is not needed to explain the change. The compile-only study [investigate/vectorizer/matmul](../investigate/vectorizer/matmul/README.md) (Compiler Explorer builds, not the toolchains timed here; nothing timed) separates compiler from library and says what changed. Observed: the same outcomes appear with libc++ 18.1.0 headers on every compiler from clang 18 to trunk, with libc++ 19.1.0 headers on clang 18, and with no library header, so the compiler version alone reproduces the pattern; clang 18 prices each of the two bounds checks at 14 units and clang 19 to 21 at 1 (the two compares are found uniform). LLVM commit `b6a8f5486b` ("[LV] Consider all exit branch conditions uniform.", 2024-04-28) is in `llvmorg-19.1.0` and not in `llvmorg-18.1.0`, `18.1.3` or `18.1.8`; that it causes the change is inferred from its diff, the changed log lines and the changed costs, since no clang 18 build with only that commit exists. Observed for the later versions: clang 22 produces the clamped trip count in an earlier pass (IndVarSimplify), and clang 23.1 and trunk (revision `efd4965724`) reject the loop again as an early-exit loop with stores; there the two loads that compute `c.size()` stay inside the loop and the clamp never appears (inferred: that this is why it is rejected; why the optimizer stopped hoisting the loads is not established). Not established either: whether the timed toolchains (Ubuntu clang 18.1.3, apt.llvm.org clang 19.1.7) print these exact costs (the decision code is the same text in those tags; distribution patches were not checked).

## What this does not show

- **Most links to GitHub Actions runs are dead for outsiders.** Run links inside `dayone/results/*/*.json`, the older `results/*/` run records and `claims-audit/` point at runs under earlier repository names and return 404 for anyone else. The exception is the twelve records in `results/s6-run-*/` and `results/s7-run-*/`: they link to runs of this repository, whose run pages are public and show each job's steps. The raw results are kept exactly as downloaded; the data in the files is complete, so every number can be recomputed from them without the runs (`python scripts/check.py`).
- **Nothing about Google's services** or the 0.30% average itself. These are 8 synthetic loops, two small programs (json and fmt, timed in the early runs; {fmt} is also a control in `realworld/`), six real-program workloads from four projects picked because they contain lost loops (plus the meshoptimizer and {fmt} controls) and a count of loops in 44 projects; no claim is made that 0.30% is right or wrong for Google.
- **One main toolchain, three newer ones on the eight loops:** Ubuntu clang 18.1.3 with libc++-18 (1:18.1.3), `-O2`, FAST mode, baseline x86-64 (SSE2) for the main timing, the census, the rewrites and the real programs; clang and libc++ 19 to 21 were timed on the eight loops only (`versions/`, above). The other toolchains (`siblings/`) are a thinner check: L1 and L2 only, 23 jobs over 2 runs on one day, many cells from a single job ("x1"), and empty pairs (GCC never ran on a usable EPYC 9V45 or on the Xeon Platinum 8573C; clang 20 never ran on the 8573C). No arm64, no AVX-512, no MSVC.
- **Shared runners, luck of the CPU.** Each job gets whatever CPU GitHub assigns. The kernel pool has 95 jobs in 15 runs: EPYC 7763 29 jobs (6 runs), EPYC 9V45 23 (13), EPYC 9V74 28 (13), Xeon Platinum 8573C 7 (6), Xeon 6973P-C 7 (6) and Xeon Platinum 8370C 1 (1). A run needs 3 jobs of a model to get its own verdict for that model, so only EPYC 7763 (5 of its 6 runs) and EPYC 9V74 (4 of 13) could be tested for whether the verdict is the same in each run, and both are; EPYC 9V45 has one run with 3 jobs, and each Xeon model has none (at most 2 jobs per run), so stability is not assessable for them.
- **The ten later runs, and the jobs they lost (`results/s6-run-*/`).** After the original 3 runs of 10 jobs, ten further runs of the same workflow added jobs: 100 dispatched, 45 returned results, and the other 55 returned nothing. The step records of the runs (public run pages; the fields used here are copied to `tests/data/s6_job_steps.json`) show where they were lost. All 100 jobs finished the timing step, in 7.5 to 10.5 minutes (9.3 minutes on average in the 55 lost jobs, 9.4 in the 45 that returned). The 55 were cancelled at the workflow's 22-minute job limit during the next step, which ran the whole-repository check (`scripts/check.py`) before the upload: 34 were still in that step and 21 had it recorded as failed, after 16.4 to 18.7 minutes. In the 45 that returned, that step took 11.3 to 16.2 minutes, except in the one EPYC 7763 job, which took 19.1. 31 of the 45 are also marked cancelled on the run pages: they passed the limit and finished the check and the upload before the job ended. The limit is 45 minutes now, the upload comes first and the job checks only its own file. The cut fell unevenly by CPU model: the 45 returned jobs are EPYC 9V74 18, EPYC 9V45 15, Xeon 6973P-C 6, Xeon 8573C 5 and EPYC 7763 1, against 19 of the first 30 jobs on EPYC 7763. The CPU models of the 55 lost jobs are not recorded in `results/`, so that the cut fell mostly on EPYC 7763 is inferred (from the one 7763 job's slow check and the 7763 share of the first runs). The timings of the returned jobs are complete; what the uneven mix does to the ratios was not tested. All 45 returned jobs passed the same completeness checks and none was excluded. The rules (`harness/criteria-v3.json`) are unchanged; they were written after the earlier results (v3 itself was), so this later data is not a pre-registered test either. Pooled with the original 30 jobs into the 75-job pool (`results/s6-pooled/`), no lost-loop cell on an AMD model moved by more than 0.05 (the lowest and highest cells are 2.805 and 8.009 against 2.797 and 8.014 in the original pool; EPYC 7763 gained one job, so for it this comparison says almost nothing); the Xeon 8573C went from 1 job to 6, and the Xeon 6973P-C, absent before, had 6.
- **The two newest runs (`results/s7-run-*/`).** Two further runs of the same workflow were dispatched on Oct 16 with the job limit raised to 45 minutes, to check that jobs return after the change; they were not chosen on their results. All 20 jobs dispatched returned results (step records in `tests/data/s7_job_steps.json`, same format as for the ten runs): EPYC 7763 9, EPYC 9V74 5, EPYC 9V45 3, Xeon 6973P-C 1, Xeon 8573C 1 and Xeon 8370C 1. The timing step took 8.6 to 10.6 minutes (7.5 to 10.5 in the ten earlier runs) and the whole-repository check, which still ran before the upload in those runs (the workflow has since been changed to upload first), 20.1 to 33.5 minutes (11.3 to 19.1 in the jobs of the ten earlier runs that returned). The two steps together took 28.9 to 43.7 minutes, setup not counted, so every job ran past the old 22-minute limit and returned, and the slowest left 1.3 minutes of the 45. That supports the account above (the earlier loss came from the check step and the old limit, not from the timing); it is one observation of 20 jobs, and the margin is small. With these 20 jobs added (95 jobs) the lowest and highest lost-loop cells are 2.806 and 8.005, and no lost-loop cell on an AMD model is more than 0.05 from its value in the original pool (the largest move is 0.044). The runs changed one verdict, the Xeon 6973P-C's, from INCONCLUSIVE to MAP (above); the verdicts of the three AMD models and of the Xeon 8573C did not change.
- **Machine state (`environment/`, run 38475747739).** The harness pins one vCPU, but the main runs recorded nothing about the machine. One run of 10 jobs on clang 18 (EPYC 7763 5, 9V45 1, 9V74 4) recorded steal, reported CPU MHz and topology per timed process. Steal share was 0% in every job (0 of 6,400 processes; large would be above 0.5%); reported MHz drifted at most 0.57% between the halves of a job and 0.04% between checks-off and checks-on processes (large: above 1%); leaving out steal-affected processes left out none, and no cell moved. The driver was seen on a hyperthread sibling of the pinned vCPU in 8 of 10 jobs, and on the pinned vCPU itself in 4; it waits while a loop is timed, so this matters only for other work on the sibling, which was not recorded. It is a real feature of the setup; alternating the builds should largely cancel it in a ratio, which was not measured here. A guest may report a constant or nominal MHz and hide real frequency changes; the reading was not constant, and no cpufreq files exist in these VMs. No cgroup CPU limit.
- **Holdout (`results/s5-holdout/`).** `PREREGISTRATION.md` was committed before its three fresh runs; the rules (`harness/criteria-v3.json`) and `harness/pool.py` were unchanged. Compared with the original 30-job pool (the 65 later jobs came after the holdout and are not part of it): EPYC 7763 (19 jobs both times) and 9V74 (5 vs 6) gave MAP both times with nearly the same costs (7763: median 5.01x vs 5.04x); EPYC 9V45 was MAP with 5 jobs and INCONCLUSIVE with 3; the Xeon 8573C drew too few jobs both times. See `RESULT.md`.
- **Independence of repetitions (`robustness/`, exploratory).** From the stored raw samples only, on the original 30-job pool, the holdout, the 75-job pool and the 95-job pool: lag-1 autocorrelation of the per-repetition log ratio has a median of -0.02 to +0.07, and the median block-bootstrap interval is 0.75 to 1.00 times the harness's width. On the 95-job pool a block bootstrap over ABBA quartets changes no lost-loop classification, no placement flag and no verdict form on any of the five models; EPYC 7763, 9V74 and 9V45 are MAP under all eight interval methods tried (on the original 30-job pool EPYC 9V45 was inconclusive under three) and the Xeon 8573C is INCONCLUSIVE under all eight. The Xeon 6973P-C is MAP under seven of the eight and INCONCLUSIVE only under the first form of the lag-1 correction, whose widths the report calls an artefact; its decisive cell (stencil at L2) has an upper end of 1.018 as pooled and 1.010 under the block bootstrap, against the 1.02 limit. In the 75-job pool the two Xeon models (6 jobs each, inconclusive as pooled) depended on the method: the 6973P-C became MAP under the block bootstrap and the jobs-only intervals, and the 8573C became MAP only under the jobs-only intervals, where a placement flag removed a forward add costing 1.057x from the forward rule; with the seventh job of each that dependence is gone for the 8573C and reduced for the 6973P-C, whose form now depends on the set of jobs (above). See [`robustness/report.md`](../robustness/report.md).
- **EPYC 9V45's MAP rests on one borderline call.** In the 95-job pool the verdict leaves out `k02_add_fwd.L1`, `k02_add_fwd.L2` and `k03_stencil.L1` as placement-sensitive (`k02_add_fwd.L2` joined the set with the jobs added after the original pool, and the set did not change with the last 20). For `k03_stencil.L1` the interval of the placement statistic ends at 0.9917, under 1 (0.9996 in the original 30-job pool). Counted as a judged forward cell, its aligned interval would reach 1.0204, above the 1.0200 limit by 0.0004 (1.024 in the original pool), and the verdict would not be MAP.
- **Intervals still understate run-to-run spread.** The pooled interval resamples jobs as well as repetitions, but a bootstrap over jobs understates the spread between jobs (`harness/criteria-v3.json`, `few_jobs_caveat`, written for 3 to 5 jobs; the AMD models now have 23 to 29 jobs and the Xeon models 7). Across the runs that have 3 or more jobs of a model, a run's point fell outside another run's interval 168 times out of 640 on EPYC 7763 (26%, largest gap 1.28%) and 62 times out of 384 on EPYC 9V74 (16%, largest gap 2.87%); the other models have fewer than two such runs to compare. In the 75-job pool the counts were 32 of 192 (17%, largest gap 0.63%) and 28 of 192 (15%, largest gap 1.75%): the share outside rose as runs were added, so the disagreement between runs did not shrink with more data.
- **The rules were changed after results, in the open.** There are four rule files, each committed before the runs it judges. The day-one criteria (`dayone/criteria.json`, 176be71) were fixed before the day-one runs; both runs failed their forward rule (one cell in run 1; two in the rerun, one of them the same stencil cell, so two distinct cells in all), so the day-one verdict is NO-GO, on record in [docs/dayone-results.md](../docs/dayone-results.md). `harness/criteria.json` (v1, 539db4a) was committed after both NO-GO runs and loosened the forward ceiling from a fixed 1.02 to 1 + max(2%, 2 x A/A). `harness/criteria-v2.json` (2473118), written after the S1 and S2 results, added the aligned column, the layout A/A and placement-sensitive cells. `harness/criteria-v3.json` (3c23b9a, its random generator corrected in 2e43fb2 before any pooled run), written after S3 and its audit, replaced the placement-sensitive rule and pooled per CPU model. v2 and v3 were written knowing earlier results, so they are not pre-registered; they added rules but changed no threshold.
- **The forward verdict leans on placement calls.** A forward cell whose as-compiled and aligned times differ, and whose hot loop sits differently, is listed and left out (`k02_add_fwd` at both sizes and `k03_stencil.L1` on all three AMD models; on the Xeon models `k02_add_fwd.L2` (8573C), `k02_add_fwd.L1` and `k03_stencil.L1` (6973P-C)).
- **The whole-program columns are an upper bound, not a confirmation.** json and fmt (earlier runs, S3) are "consistent with at most 0.2% to 3.3%", each next to its own A/A floor (0.2% to 2.4%); that wording is an upper bound only where the interval includes 1. In 3 of the 9 json job rows the interval lies wholly above 1, so a small slowdown is indicated in those rows, not only an upper bound (only for the first does the lower end of the interval, 1.5% above 1, also clear that job's own A/A floor of 0.90%; for the second and third the lower end, 0.3% above 1, lies below their floors of 0.86% and 0.58%): EPYC 7763 twice in the S3 full run (point ratios 1.024 and 1.010, intervals 1.015 to 1.032 and 1.003 to 1.022, A/A 0.90% and 0.86%) and Xeon 8370C once in the audit run (1.009, 1.003 to 1.016, A/A 0.58%). The other six json rows, including the 7763 reproduction run (1.002, 0.996 to 1.014), and no fmt row have an interval wholly above 1. In these single jobs a difference of 0.30% is not reliably above the noise; pooled over 29 jobs, the kernel A/A floor on EPYC 7763 is about 0.07% (0.070%), and that floor belongs to the byte-identical kernel binary, not to these programs. The pooled kernel runs time the kernels only. RAM-size cells did not reproduce in the early runs and are not in the pooled runs.
- **Six real-program workloads from four projects, timed whole (`realworld/`).** The workloads are LightGBM with three option sets (default, multiclass, linear), Draco, tiny-dnn and Spectra, picked because they contain lost loops; meshoptimizer and {fmt} are controls without any. Pooled per CPU model over 24 distinct jobs in 6 runs: AMD EPYC 7763 16 jobs, EPYC 9V45 5 jobs, EPYC 9V74 3 jobs (3 is the minimum for a reading). The result differs by model. On EPYC 7763, five of the six workloads (three of the four projects) ran detectably slower with the checks on, by 1.2% to 7.5% across the as-compiled and aligned columns; Spectra was not detectable (at most 0.5%). On EPYC 9V74, four of six workloads (LightGBM default, multiclass and linear, Draco) were detectable, 0.7% to 7.1%; tiny-dnn (at most 1.2%) and Spectra (at most 1.6%) were not. On EPYC 9V45, three of six workloads (LightGBM default and multiclass, Draco) were detectable, 2.3% to 5.4%; LightGBM linear (at most 8.4%, and its two columns disagree: 1.007 as compiled, 1.078 aligned), tiny-dnn (at most 19.3%, and its two columns disagree: 0.93 as compiled, 1.19 aligned) and Spectra (at most 2.1%) were not. So "five of six workloads" holds on EPYC 7763 only. On every model the meshoptimizer control was not detectable and the {fmt} control was faster or not detectable (on 7763 1.5% to 5.6% faster, a placement effect that was not explained). Cachegrind puts the lost loops' own lines at 0.0002% to 6.3% of executed instructions, so for LightGBM (default and multiclass), Draco and tiny-dnn (under 1% on the lines; tiny-dnn's functions hold 16%, so for it this is weaker) the data are consistent with most of the cost being checks elsewhere; which checks was not isolated. Limits: no profile-guided optimization in this timing (see the PGO column below), shared virtual machines, one toolchain, three AMD CPU models only (16, 5 and 3 jobs), workloads picked because they contain lost loops (not a sample of any production code). It neither confirms nor contradicts 0.30%. Of the 8 expectations written before any run, 5 held (`realworld/PLAN.md`, `realworld/README.md`).
- **The census counts loops, not time.** A lost loop is only potentially expensive; how hot it is cannot be known at compile time. A template loop counts once per function it was compiled into (distinct source locations are given beside each count). The project selection is the author's, written down before compiling ([corpus/PLAN2.md](../corpus/PLAN2.md)), not a random sample of C++.
- **Layout sweep (`layout-sweep/`, three runs pooled in `layout-sweep/results/pooled/analysis.json`, rules in `layout-sweep/PLAN.md` amendment 1).** Does the forward-loop claim survive moving the loop in memory? Coarse mode: 4 placements (the kernel function moved by 0, 16, 32 and 48 bytes, so the hot loop starts at those offsets modulo 64), the placements the compiler can produce itself, not a full sweep. Four kernels (forward sum, forward add, stencil, reverse), sizes L1 and L2, pooled per CPU model: EPYC 7763 8 jobs, EPYC 9V74 8, EPYC 9V45 4, Xeon 8573C 2 and Xeon 6973P-C 2 (the two Xeon models are below the minimum of 3 jobs: inconclusive). The reverse loop stays 5.2x to 8.0x at every placement on the three EPYC models (7763: 7.6x to 8.0x; 9V74: 5.4x to 8.0x; 9V45: 5.2x to 6.0x). The forward sum is robust everywhere (0.999 to 1.007). The forward add is MIXED on 7763 and 9V74: 0.826 to 1.585 on 7763 and 0.824 to 1.596 on 9V74 at L1, where the as-compiled placement is the slow one and the aligned build is 0.834 and 0.825; on 9V45 it is ROBUST at L1 (median 0.837, 4 of 4 placements pass). The stencil at L1 on 7763 is placement-dependent (median 1.054, 3 of 4 placements cost, 0 pass); on 9V45 its L1 cell is the only inconclusive EPYC cell (A/A half-width 2.18%, above the 2.0% limit); on 9V74 its L2 cell is MIXED (one placement at 1.046). So "forward loops near 1x" holds for the sum and is placement-dependent for the add and the stencil on some models. The page has the tables (`details.html`, section 3b).
- **PGO column (`pgo/`, six runs: 38440131645, 38440143122, 38440153847, 38447188298, 38447199564 and 38447211726, on build run 38438892253).** All eight rows (six workloads and two controls) rebuilt with clang instrumented profile-guided optimization, each mode profiled separately, 24 distinct jobs pooled per CPU model (EPYC 7763 12, EPYC 9V74 5, Xeon 8573C 6, Xeon 8370C 1). EPYC 7763 (non-PGO 16 jobs) and EPYC 9V74 (non-PGO 3 jobs, the minimum) have a reading on both sides. On EPYC 7763, PGO FAST/NONE as compiled: LightGBM default 1.012 (not detectable, at most 3.43%), multiclass 1.023, linear 1.050, Draco 1.087, tiny-dnn 1.031 (the last four detectably slower), Spectra and meshoptimizer not detectable, {fmt} faster; against the non-PGO ratios PGO was lower in one row, higher in two and not detectably different in five. On EPYC 9V74, three rows with lost loops stay detectably slower under PGO (1.023 to 1.090); PGO was lower in one row, higher in one and not different in six. PGO leaves the cost in most rows that had one (LightGBM default dropped to not detectable on both models), and almost all of the census's lost loops stay lost (19 of 53 locations vectorized with checks off, 1 with checks on). Limits: the training input is the timed input, which flatters PGO; instrumented profiles only, no sampling profiles, no link-time optimization; the two Xeon models have no non-PGO counterpart, so neither is read. `pgo/report.md` is the full report.
- **The lostloops tool, run live (`tools/lostloops/`, run 38438713384, Ubuntu clang 18.1.3).** On leveldb, Spectra and LightGBM at the census's pinned commits its lists matched the census exactly. One run on three projects, not a general guarantee.
- **Google's own post adds context this project only partly tests:** it notes that a handful of performance-critical code paths still needed explicitly unsafe accesses, and that profile-guided optimization further improved performance (it adds that the overhead of bounds checking remains minimal even without such techniques). The PGO column above is one test of the second point, with the training input equal to the timed one.
- **No rewrite is called "better".** Under the mitigation rules written before its first timed run (`mitigate/criteria.json`), a job counts only if all 8 of its A/A controls are under 2%, and only 2 of 12 jobs met that (both on EPYC 7763). The mitigation timings are measurements on AMD only (EPYC 7763, 9V45 and 9V74; no Intel model was drawn in 12 jobs), and EPYC 9V45 charges the reverse rewrites 6% to 9% for a reason not found.

## How it works

- **Kernels** (`kernels/`): one `noinline` function per loop shape on `std::vector<int32_t>` through `operator[]`, at working-set sizes computed from the runner's real caches (L1, L2; RAM in the early runs). Each prints a checksum; NONE and FAST must match.
- **Builds**: NONE (`-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_NONE`), FAST (`..._FAST`), NOVEC (NONE plus `-fno-vectorize`), and an **aligned pair**: NONE and FAST again with `-falign-loops=64`, so placement luck can be told apart from the check. Recorded per build: sha256, the compiler's vectorization remarks, the number of check traps (`ud2`) in the kernel, its assembly and the NONE-to-FAST diff, and Cachegrind instruction counts (labelled "instructions, not time").
- **Timing**: 40 repetitions per side in ABBA order (20 in the earlier runs), pinned to one CPU, timed inside the binary. Per job, ratio = median FAST / median NONE.
- **Pooling** (`harness/pool.py`, rules in `harness/criteria-v3.json`): every job of the same CPU model, across runs, is pooled as the geometric mean of the per-job ratios. The 95% interval is a two-level bootstrap (jobs, then repetitions inside each job, 2,000 resamples, a fixed generator), so it includes the spread between jobs. `harness/pool_check.py` recomputes it independently.
- **Controls**:
  - **A/A**: the NONE binary timed against a byte-identical copy, pooled per CPU model.
  - **Layout A/A**: NONE against NONE built at a different loop alignment, which measures what placement alone can do.
  - **Negative**: the forward loops, vectorized in both builds, expected near 1.0x.
  - **Positive**: reverse, stride-2 and matrix multiply lose vectorization under FAST (confirmed in the remarks and the assembly), and the NOVEC build shows what switching vectorization off costs on its own.
- **Verdict**: MAP, HOLDS EVERYWHERE or INCONCLUSIVE per CPU model with at least 3 jobs, and whether it is the same in every run with enough jobs. There is no single page-level form. Nobody edits the line by hand.
- **Follow-ups**, each with its own workflow, results folder and README:
  - `corpus/`: the census. Every translation unit of 44 pinned projects compiled NONE and FAST; lost loops matched from clang's optimization records, check traps counted with `objdump`, and each lost loop traced, where the trace links, to the libc++ check inside it. Controls: the 8 kernels must come out as expected, and the whole census runs twice and must be byte-identical. The kernel control failed as registered at `-march=x86-64-v3` (matrix multiply stays vectorized there); the others passed.
  - `mitigate/`: rewrites of the four loops that pay, each checked for vectorization, traps, checksum and a one-element-short safety test, then timed.
  - `siblings/`: the same 8 kernels under clang 18 EXTENSIVE and DEBUG, `-march=x86-64-v3`, GCC 14 with `_GLIBCXX_ASSERTIONS` at `-O2` and `-O3`, and clang 20 with libc++ 20.
  - `investigate/`: why `k02_add_fwd` cost 1.6x on some CPUs; `investigate/vectorizer/`: compile-only studies on Compiler Explorer (saved answers, offline checks) of which pass and which cost decision stops the vectorizer, for the reverse and stride-2 loops and for matrix multiply.

  - `versions/`: the same 8 kernels under clang and libc++ 19, 20 and 21 (apt.llvm.org), timed like the main study; `environment/`: steal, reported frequency and core sharing on the runners.
- **The page** (`site/`): the claim, the verdict per CPU model, the map of every cell with its interval, and a drawer per loop with the exact build commands, the instruction ratio, the compiler's verdict in plain words and the marked assembly diff. Live at https://jacobopacheco.github.io/third-of-a-percent/ (`.github/workflows/pages.yml` publishes `site/` on every push to `main`). To look at it locally:

```
python -m http.server 8000 --directory site
# then open http://localhost:8000
```

                (s1 to s4, s4-pooled, s6-run-*, s6-pooled, s7-run-*, s7-pooled, s5-holdout, corpus*, mitigate*, siblings*, realworld*, ...),
                plus fixture.json (SAMPLE data)

                loops lose SIMD and why matrix multiply is kept on clang 19 to 21

## About the commit hashes

The rule files and the page cite commit hashes from the original development history, which is not published here. Each rule file records when it was written in its own `written` field. Some rule files and code comments also cite planning documents (a day-one plan, a specification and a review of the idea) that are not published; the verdict rules themselves are stated in full in `dayone/criteria.json` and `harness/criteria*.json`, and `dayone/evaluate.py` and `harness/` implement them. The rule file `dayone/criteria.json` is quoted as committed. It cites `docs/PLAN.md`, `docs/SPEC.md` and `docs/skeptic.md`, which do not exist in this repository, and it calls an earlier reading of Compiler Explorer output the "skeptic" reading: that was a review of the idea made before the first run, which expected forward loops to stay vectorized under FAST and reverse and strided loops not to. The day-one run then checked this with the compiler remarks (see `docs/dayone-results.md`). The file is not edited because its SHA-256 is recorded in the raw day-one records as the proof that the rules were fixed before the results; the same holds for the `harness/criteria*.json` files. Run links stored in the older raw records point at runs executed in a different repository and return 404 for outsiders; the records of the ten later runs (results/s6-run-*) link to public runs of this repository. All records are kept as downloaded.
