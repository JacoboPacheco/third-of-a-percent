# Matmul (k08) under FAST: lost on clang/libc++ 18, kept on 19 to 21 (what is and is not established)

Status: partly shown, partly inferred. The "why" at compiler-source level is NOT shown.

Later work: the open questions below (what changed between clang 18 and 19, and whether the library or the compiler is responsible) are addressed, with every claim labelled observed, inferred or not established, in the compile-only study [`investigate/vectorizer/matmul`](../investigate/vectorizer/matmul/README.md). This note is kept as written.

## What was compared
- clang 18 asm and remarks: `results/s3-audit-run-38127024171/results-amd-epyc-9v45-96-core-processor-j2/{asm,remarks}/k08_matmul.{none,fast}`.
- clang 19 asm and remarks: `versions/results/38471430657/versions-19-amd-epyc-7763-64-core-processor-j10/...` (20 and 21: remarks and a grep of the asm only).
- Same source (`kernels/k08_matmul.cpp`), same flags (`-O2 -std=c++20 -stdlib=libc++`, harness/run.py). The two files come from different CPU models (EPYC 9V45 for clang 18, EPYC 7763 for clang 19). The asm does not depend on the CPU (no `-march`), but no clang-18 build from a 7763 job was diffed, and nothing was recompiled when this note was written.

## Shown (read from the files)
1. Clang 18, NONE: inner loop `vectorized loop (vectorization width: 4, interleaved count: 2)`.
2. Clang 18, FAST: remark `the cost-model indicates that vectorization is not beneficial`. The asm is a scalar inner loop of 12 instructions with two bounds checks per element (`cmp; jbe -> ud2` for `b[k*d+j]` and `c[i*d+j]`), no packed instructions (0 matches for padd/pmul/pshuf).
3. Clang 19 (and 20, 21), FAST: the same loop is `vectorized loop (width 4, interleaved count 2)`. The vector body (8 ints per trip, `pmuludq`/`paddd`) contains no `ud2` branch and no bounds check. The checks sit outside it: (a) a check of `a[i*d+k]` once per (i,k); (b) a block of `cmp/cmov` that clamps the trip count to the largest index that passes both size checks (it reads vector end minus begin for b and c); (c) a runtime overlap test (c vs b) that falls back to the scalar loop (the NONE build has the same test, as `cmp/setb/and/or` at 12dd to 12f4 of `k08_matmul.none.s`; FAST computes its end pointers from the clamped trip count); (d) a scalar remainder loop that still has both checks and the `ud2` exits. A single `ud2` target remains in the function for 19, 20 and 21 (in the 18-FAST asm also one).
4. Clang 19 NONE and FAST use the same vector body (same instructions; SSE2 only, no AVX2). FAST adds the size checks, the trip-count clamp and a scalar remainder that carries both checks; the overlap test is in both builds.
5. Measured on EPYC 7763 (versions/results/38471430657, j10): FAST/NONE 1.61 at L1 (d=36 inner trip count, 15,552 B) and 1.15 at L2 (d=147, 259 KB). Clang 18.1.3 on EPYC 7763 measured 3.2 at L1 and 3.8 at L2 (`results/s3-run-38121166129`, two jobs that agree: 3.175 and 3.171 at L1).
6. A build of the same kernel with no vectorization at all (the no-vectorize control, `-fno-vectorize`) costs 1.6 at L1 and 1.7 at L2 against the NONE build (the same two jobs: 1.625 and 1.622 at L1, 1.740 and 1.737 at L2; the 19-job pool on EPYC 7763 in `results/s4-pooled/pooled.json`: 1.63 and 1.75). So on clang 18 only part of the 3.2 and 3.8 is the lost SIMD, and the 1.6 at L1 on clang 19 to 21, which keep SIMD, is as slow as the build without SIMD.
7. Compile-only sweep (`ce-sweep/README.md`, each compiler with its own libc++, SSE2 target): matmul is lost on clang 16, 17 and 18.1.0, kept on 19.1.0 to 22.1.0, and lost again on 23.1.0 and trunk. Only clang 19, 20 and 21 were timed; 22, 23.1 and trunk were not. Ubuntu's own clang 20.1.2 with libc++ 20 also keeps the loop vectorized (`siblings/README.md`, row clang20-fast).

## Inferred (consistent with the above, not proven)
- Clang 19 at SSE2 turns the per-element `index < size` checks into a bound on the trip count (check hoisting / loop predication of an invariant-stride check), after which the vectorizer sees a countable loop with no side exits. At SSE2, clang 18 left the checks in the loop, and the remark then says the cost model rejects vectorization. That the exits are the reason for the 18 rejection is an interpretation: the remark says "cost model", not "legality".
- At x86-64-v3 on Compiler Explorer, clang 18.1.0 already emits a similar structure, so the hoisting may not be new in 19; that build uses the AVX2 cost model and pairs with its own libc++ rather than Ubuntu's 18.1.3, and no SSE2 or Ubuntu 18.1.3 build was found to show the same. The cached output (`ce-sweep/cache/clang1810__x86-64-v3__O2__hardened.json.gz`) contains, for this kernel: a `cmp/cmov` clamp of the trip count (including `and edi, 7 / mov edx, 8 / cmove rdi, rdx`), a check-free `vpmulld` loop and a scalar tail that keeps the checks. At x86-64-v3 matmul is not lost on clang 18 (`ce-sweep/README.md`). What differs between 18 and 19 at SSE2 is the vectorizer's decision (18: "the cost-model indicates that vectorization is not beneficial"; 19: vectorized, width 4, interleave 2). Whether clang 18 at SSE2 lacks the clamp or rejects the loop before using it is not shown, and neither is the cause.
- The remaining 1.61x at L1 is the overhead around the vector body: the code run once per (i,k) pair (index clamps, overlap test, stack spills) is amortized over only 36 elements. Both builds leave 4 elements (36 mod 8) to a scalar tail; in FAST that tail carries both checks and takes 12 instructions per element, where the NONE tail is unrolled by two (9 instructions per two elements). The FAST function is also 62 disassembly lines longer than NONE (203 against 141, a rough count that includes padding). At L2 (147 elements) the same overhead is spread wider, which fits 1.15x. The prologue cost was not measured separately (no performance counters, no instruction-level timing), so the split is an estimate.

## NOT shown
- Which LLVM change between 18 and 19 changed the vectorizer's decision at SSE2. LLVM was not bisected and its release notes and commits were not read, so the pass or patch is not identified, and why the decision changed is not established.
- Whether it is a libc++ change (how `operator[]` hardening is written) or an LLVM optimizer change. Both toolchains' libc++ differ (18 vs 19), the compiler too; nothing here separates them. A test that would: compile the clang-19 library headers with clang 18 or the reverse (not run). The compile-only sweep (Shown, item 7) and the Ubuntu clang 20.1.2 build each pair a compiler version with its own libc++, so neither separates the library from the compiler.
- Other loops: this says nothing about why reverse and stride-2 stay lost on 19 to 21, only that matmul's inner loop (forward, unit stride, checks on loop-linear indices) is the one whose checked version the vectorizer accepts from clang 19 to 22 at SSE2. The cause is not claimed.
