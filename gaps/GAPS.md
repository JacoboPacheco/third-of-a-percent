# Related work: sources read for this study

Written Mon Oct 12 2026. Public sources on the same question, each with what was read of it and how this project differs. Sources known only from search summaries are labelled as such.

## What the comparable work says

| Source | What it is | What was read | What it has that this project lacks | What this project has that it lacks |
|---|---|---|---|---|
| Google Security Blog, Nov 15 2024, https://security.googleblog.com/2024/11/retrofitting-spatial-safety-to-hundreds.html | The 0.30% claim | Full post text (downloaded HTML): "average 0.30% performance impact across our services"; one unnecessary check fixed took overhead "from 0.35% to 0.3%" and went upstream; PGO "further improved performance"; "a handful of performance-critical code paths still require targeted use of explicitly unsafe accesses"; 1,000+ bugs; 30% fewer segfaults | Fleet scale, production workloads, an upstream fix; the post says PGO "further improved performance" but not whether the 0.30% includes it | Any per-loop breakdown, machine code, controls, a method a stranger can rerun |
| Dionne, Rebert, Shavrick, Varlamov, "Practical Security in Production: Hardening the C++ Standard Library at Massive Scale", ACM Queue 23(5), 2025, https://queue.acm.org/detail.cfm?id=3773097 | The sequel, with the method | Article text in the browser: "key services were benchmarked"; "PGO ... This was critical. High-quality PGO data allows the compiler to identify hot paths and often move checks out of the hot paths"; only five services opted out entirely; the fine-grained unsafe-access API "was used in just seven distinct places"; binary size 2% reduced to under 0.5% by a non-verbose mode; per-TU enablement via ABI tags | PGO as a measured factor; adoption numbers (5 services, 7 sites); binary-size cost | Which loop shapes are the 7 sites' kind; a count of such loops in open code (`corpus/`) |
| Chandler Carruth, "Story-time: C++, bounds checking, performance, and compilers", Nov 2024, https://chandlerc.blog/posts/2024/11/story-time-bounds-checking/ | Why it got cheap | Post: credits LLVM check optimization driven by Java/Rust/Swift, UBSan work, and PGO; says without PGO overhead would not be tolerable for most performance-sensitive workloads; warns that benchmarks of pervasive patterns skew toward confirmation bias | The expert framing a reviewer will quote: PGO matters | A test of that framing on loops |
| libc++ Hardening Modes docs, https://libcxx.llvm.org/Hardening.html | The mode definitions | Page: FAST = `valid-element-access` + `valid-input-range`, "relatively little overhead"; EXTENSIVE "recommend benchmarking"; no numbers, no mention of vectorization | Authority | The only public per-loop numbers for FAST that this search found |
| RFC: C++ Buffer Hardening, LLVM Discourse, Oct 5 2022, https://discourse.llvm.org/t/rfc-c-buffer-hardening/65734 | The design RFC (Korous et al., Dionne on libc++) | First page: one reply claims "20% overhead everywhere" with no data; another reply's microbenchmark shows no difference (~31.3 us each) | Nothing measured | Measured answer to exactly that argument: both are right, depending on loop shape |
| Popescu, Xu, Apostolakis, August, Levy, "Safer at Any Speed" (NADER), OOPSLA 2021, https://www.cs.princeton.edu/~npopescu/papers/nader.pdf (doi 10.1145/3485480) | The closest academic study (Rust) | PDF text: 76.4% of benchmarks of top Rust crates show little or no or negative cost from unchecked indexing; 23.6% more than 1% slower with checks, 11.8% more than 1% faster; brotli overhead 7.7% / 6.5% (older rustc) / 2.5% (Apple M1) / 4.4% (other workload); ~200 benchmarks, 95% CIs; ACM artifact badges; a tool (NADER) | Corpus of ~200 real benchmarks timed; multiple architectures (x86 and M1); an artifact on Zenodo; a tool with an end-to-end evaluation | They attribute checks-make-it-faster results to code layout and inlining heuristics but never control layout; this project does (aligned pair, layout A/A, `investigate/FINDINGS.md`) |
| Flater and Guthrie (NIST), "A Case Study of Performance Degradation Attributable to Run-Time Bounds Checks on C++ Vector Access", J. Res. NIST 118, 2013, https://pmc.ncbi.nlm.nih.gov/articles/PMC4487316/ | The classic C++ study | Article: GCC 4.6.2, one Xeon X5450 box with frequency scaling off, 63 runs per cell, Latin-square order, Sidak-corrected intervals; `vector.at(i)` (0.881 +/- 0.009)% slower than C `array[i]` at -O3; sequential write loops only; vectorization never analysed | Bare metal with frequency scaling off; a far tighter interval; a formal multiple-comparison correction | Loop shapes beyond forward; the vectorization mechanism; modern toolchains; the finding that the shape, not the check, decides |
| Readyset, "How much does Rust's bounds checking actually cost?", https://readyset.io/blog/bounds-checks | Practitioner whole-program test | Post: patched rustc to drop all bounds checks; 1,227 checks per warm read; results "well within the noise threshold"; no hardware or run count stated | A whole real program timed with every check removed (a compiler patch) | Controls, intervals, A/A, machine code |
| Shnatsel, "How to avoid bounds checks in Rust (without unsafe!)", https://shnatsel.medium.com/how-to-avoid-bounds-checks-in-rust-without-unsafe-f65e618b4c1e | Practitioner guide | Search summary only (not opened): typical gains 1-3%, worst seen 15%, large when removal enables vectorization | Mitigation patterns written for practitioners, widely read | Measured mitigations for C++ (`mitigate/`) |
| Mytkowicz, Diwan, Hauswirth, Sweeney, "Producing Wrong Data Without Doing Anything Obviously Wrong!", ASPLOS 2009, https://sape.inf.usi.ch/publications/asplos09.html | Measurement bias | Summary page and abstract: link order and environment size change measured speedups enough to reverse conclusions; survey of 133 papers found none adequately addressed it; remedy: setup randomization and causal analysis | Setup randomization over many layouts | A causal analysis of one layout effect (k02) that changed the result |

| Coz, https://github.com/plasma-umass/coz (SOSP 2015 best paper) | Causal profiling | README: virtual speedups predict what optimizing a line buys end to end | The link from a loop's cost to whole-program cost | n/a (different question) |

Searched and NOT found: any public per-loop-shape measurement of libc++ FAST (LLVM docs, Discourse, GitHub issues, Phoronix, Chromium spanification commits, Microsoft STL `_MSVC_STL_HARDENING` docs). Chromium's Tint docs keep plain indexing in hot UTF-8 loops for speed, with no numbers. That absence is this project's opening; it also means a reviewer has nothing to calibrate against except Google, NADER and NIST.
