# Third of a Percent

[![ci](https://github.com/JacoboPacheco/third-of-a-percent/actions/workflows/ci.yml/badge.svg)](https://github.com/JacoboPacheco/third-of-a-percent/actions/workflows/ci.yml)

A bounds check makes a C++ program stop if an index is out of range; libc++ hardening turns these checks on in the standard library. Google reported that this costs 0.30% on average across its services, a third of a percent. Measured one loop at a time, the same checks make some loops (reverse, stride-2, matrix multiply) take 2.8 to 8.0 times as long as the same loop without them, at the study's sizes (x86-64, one compiler version, data that fits in the CPU cache). This repository holds that measurement, the machine code that explains it, and one command that re-checks every stored measurement and verdict (what it does not cover is listed under "Check it yourself").

A measurement study, not a library or a tool to install, for C++ engineers and tech leads deciding whether to turn on libc++ hardening. **Start here: the live page, https://jacobopacheco.github.io/third-of-a-percent/** Switch the check off and on, then pick a loop to read its machine code.

Status: work in progress (Oct 2026). The measurements described here are the ones so far; the page, notes and results may still change. Code written by AI coding agents directed by the author.

## In three sentences

1. Google reported that turning on bounds checks in C++'s standard library cost its services 0.30% on average.
2. This study built algorithm kernels and real programs with the checks off and on, timed each pair 20 to 40 times per side in alternating order against an A/A control (a program timed against a copy of itself, to see the machine's own noise), and showed from the machine code that the checks were there.
3. The average hides a map. On clang 18, libc++ 18 and `-O2`, loops where the check stops the compiler from using SIMD (working on several array elements per instruction; reverse, stride-2, matrix multiply) took 2.8 to 8.0 times as long in cache at the study's sizes (the smallest as compiled, the largest with the loops aligned).

Loops that count upward to the container's own `size()` (forward loops bounded by `size()`) kept SIMD and cost little on the AMD models once code placement is controlled. Forward loops with another bound, a variable `n`, were timed separately and that sentence does not cover them: on the two x86-64 models read, the sum with a variable bound took 1.985 to 2.043 times as long with the checks on, where 0.97 to 1.35 was predicted (see [Forward loops with a variable bound](#forward-loops-with-a-variable-bound)). A gather through an index, which neither build vectorizes, costs 1.6x to 2.8x at L1 depending on the CPU model, so the cost is not only a SIMD effect. The Intel and Arm results, with what each verdict means, are under [Results by CPU model](#results-by-cpu-model).

## Check it yourself

The live page above needs nothing installed. The rest of this section is optional, for re-checking the numbers: clone this repository and run the check:

```
git clone https://github.com/JacoboPacheco/third-of-a-percent
cd third-of-a-percent
python scripts/check.py
```

Recomputes every interval and verdict in `results/` from the raw timings and checks the page's data. It needs Python 3 (CI runs 3.12; `python3` where that is the interpreter's name), numpy and PyYAML (`pip install numpy pyyaml`, or `pip install -r requirements.txt` for the same two; pytest is optional, a built-in runner is used without it) and takes roughly one to two hours on a CI runner (a laptop was not re-timed with the 95-job pool). The page check also needs playwright and network access to the fonts the page loads; what the run prints without them is under [Details of the check and the rerun](#details-of-the-check-and-the-rerun). Parts can be checked alone: `python scripts/build_site_data.py --check` (the page's data), `python replication/compare.py --verify`, `python dsweep/analyze.py --verify results/s10-dsweep-run-*` (this one needs the run folders as arguments), `python forwardt/analyze.py --verify`. The command rebuilds nothing, so compiler remarks and listings are read from the records, and it does not cover the other-toolchain table (`python siblings/summarize.py results/siblings-run-<id>`), the compile-only vectorizer studies (`python check.py` in `investigate/vectorizer/matmul/`; `python verify.py` and `python replay_check.py` in `investigate/vectorizer/reverse-stride2/`) or the full seed recomputation (`python arm64/seeds.py --check --all`).

To rerun the measurement itself, fork the repository, enable Actions in the fork and dispatch the workflow there (this needs the GitHub CLI, installed and logged in):

```
gh repo fork JacoboPacheco/third-of-a-percent --clone
gh workflow run measure.yml -R <you>/third-of-a-percent
```

Then `gh run watch -R <you>/third-of-a-percent` and `gh run download <id> -R <you>/third-of-a-percent` (the per-job files are the `results-<cpu>-jN` artifacts, the pooled result is `pooled`). How long a run takes, the runner sizes, the compiler versions and the pinned actions are under [Details of the check and the rerun](#details-of-the-check-and-the-rerun). GitHub, not you, picks each job's CPU model, and a verdict needs 3 or more jobs of one model, so one rerun will not reproduce the per-model verdicts by itself: pool several runs with `python harness/pool.py <out.json> <run folders>`, and expect some models to be missing. Keep your downloads and your pool under the git-ignored `build/` (for example `python harness/pool.py build/pooled.json build/run-*`), not under `results/`, so that `scripts/check.py` keeps seeing only the stored pools. The workflow takes one runner label per run: add `-f runner=ubuntu-24.04-arm` for the Arm column, and pool those runs apart from the x86-64 ones (the other steps are in [arm64/README.md](arm64/README.md)). If a number does not reproduce, open an issue on this repository.

## The question

Google wrote that "Hardening libc++ resulted in an average 0.30% performance impact" across its services ([Google Security Blog, Nov 15 2024](https://security.googleblog.com/2024/11/retrofitting-spatial-safety-to-hundreds.html)). Hardening makes C++'s standard library check every `vector[i]` against the vector's size.

This study timed loops and programs with checks off and on: a different measurement, so it neither confirms nor contradicts Google's average.

**Words used here.**
- **SIMD**: one instruction working on several array elements at once.
- **A/A control**: timing a program against a copy of itself, to see the machine's own noise.
- **NONE / FAST**: the same program built without checks (NONE) and with libc++'s FAST hardening mode (FAST).
- **Verdict**: the per-CPU-model reading, computed from written rules, one of three: **MAP** (costs uneven across loop shapes), small everywhere, or **INCONCLUSIVE** (cannot be called from the data: a mixed picture, too noisy, too few jobs or a failed control).
- **Placement**: the memory address where a loop's code starts; moving it can change speed.
- **Aligned**: every loop's code starts on a 64-byte boundary (`-falign-loops=64`), so differences in where a loop starts are removed from the comparison.
- **Forward sum, forward add**: `s += a[i]` and `c[i] = a[i] + b[i]` over a vector's `size()`, indices counting up.
- **PGO**: profile-guided optimization: the compiler sees a sample run first and tunes to it.

## Results by CPU model

- Forward loops bounded by `size()` cost little on the AMD models once code placement is controlled (0.82x to 1.06x aligned, one AVX2 exception, 1.11x); below 1x the checked loop ran faster (cause inferred: loop layout). As compiled, the forward add cost about 1.6x on two of the three AMD models. Loops with a variable bound are not covered by this line: see [Forward loops with a variable bound](#forward-loops-with-a-variable-bound).
- Intel: in all 29 Intel jobs seen (three models; 15 are in the 95-job pool, 5 in earlier runs, 9 more in set C) the forward add (bounded by `size()`) at L1 cost 1.05x to 1.20x aligned, against 0.82x to 0.84x on the AMD models. The Xeon 8573C (7 jobs) has no verdict (INCONCLUSIVE under the written rules): its forward add costs a measured 1.06x, over the 2% forward limit. The Xeon 6973P-C (7 jobs) has a verdict (MAP) that is borderline: with 6 jobs it was INCONCLUSIVE, its stencil at L2 ending at 1.026, over the same limit, and the seventh job moved that end to 1.018; with the bootstrap's draw no longer mattering that end is 1.0196, under the limit by 0.0004, and the whole analysis gives INCONCLUSIVE under 13 of 60 other seeds, so the word is best read as undecided; its forward add of 1.20x is left out as placement-sensitive. A third model, the Xeon 8370C, drew 1 job, too few to judge. See the [details](readme-parts/DETAILS.md).
- Arm (a separate column; the figures above are x86-64): on one Arm core type (Neoverse-N2, 30 jobs in 3 runs, the same compiler, flags and rules) reverse and stride-2 lose their NEON loops and cost 6.58x and 5.50x at L1 (all ratios here as compiled); matrix multiply keeps its NEON loop and still costs 1.55x at L1 (1.02x at L2); forward loops bounded by `size()` cost 1.000x to 1.007x at L1 (the add and the stencil are placement-sensitive and not judged), against an A/A floor of 0.009% that belongs to one L1 cell. The verdict is INCONCLUSIVE under the written rules, which stay as written: the forward add at L2, aligned, has an interval ending at 1.021, over the 1.02 limit by 0.0011, a margin inside the bootstrap's own seed noise (8 of 400 other seeds end at or above 1.02) in a cell where an identical binary is as noisy (A/A half-width 2.6%), so the data cannot separate INCONCLUSIVE from MAP there. Loops with a variable bound are timed separately on this core too (see [Forward loops with a variable bound](#forward-loops-with-a-variable-bound)). See [arm64/README.md](arm64/README.md).
- Loops that lose SIMD are rare in the general libraries counted and not rare in the numeric projects (counted, not timed).

## What was found

Some loops lose SIMD when a check is added. A check can stop the program at any element, so the compiler may process several elements at once only if it can show the whole range is in bounds. For forward loops bounded by `size()` it can (the check moves to the tail); for the reverse and stride-2 loops clang 18 reports that it cannot determine the number of iterations, and for matrix multiply that vectorizing is not beneficial. Compile-only tests narrow the cause (nothing timed; run on Compiler Explorer's clang 18.1.0 release candidate, not the timed Ubuntu 18.1.3). On clang 18, of 29 loops compiled with FAST, all 16 with an iteration count for every exit in the compiler's analysis were vectorized and none of the 13 with an uncounted exit, and hoisting the one check the reverse loop keeps inside it makes it vectorize (observed; that the vectorizer needs the count is inferred from the LLVM source; [reverse and stride-2](investigate/vectorizer/reverse-stride2/README.md)). For matrix multiply the cost model prices each of the two checks at 14 units, so a width-4 vector iteration costs 45 against 44 for four scalar ones (observed; [matrix multiply](investigate/vectorizer/matmul/README.md)).

- **2.8x to 8.0x slower** in cache, at the study's sizes, for loops that lose SIMD (reverse, stride-2, matrix multiply on x86-64 with clang 18), on all four CPU models with a verdict (three AMD, and the Xeon 6973P-C, borderline); the Xeon 8573C (no verdict) lost the same loops, and the two Xeon models (7 jobs each) range 3.2x to 6.6x. This is the main run; other setups tested separately (`siblings/`) reached about 9.7x at L1. Losing SIMD is only part of the cost: on EPYC 7763 at L1 a build with vectorization switched off by hand takes 3.3x as long for reverse (7.6x with the checks on, as compiled), 2.6x for stride-2 (5.1x) and 1.6x for matrix multiply (3.2x). The rest is presumably the per-element compare and branch, and also the four-fold unrolling that the scalar loop without the check has and the checked one lacks (read from the listings; inferred, not separated, and not a stable share: on Neoverse-N2 the no-vectorize build takes 5.5x and the checked build 6.6x for reverse).
- **1 of 593** vectorized loops in 19 general libraries lose SIMD, against 444 of 4,968 in 25 numeric projects. Counted, not timed. Of the 593, 443 are inside libc++'s own headers and none of those was lost; counting project code and the census's own driver files, it is 1 of 150 against 444 of 1,609 (one of those 1,609 is a driver loop). In the numeric set 7 of 25 projects have any lost loop, and LightGBM holds 331 of the 444. To list these loops in your own code, see `tools/lostloops/` (run from that folder: `python3 lostloops.py --compile-commands build/compile_commands.json --out lostloops-report`; example workflow: `tools/lostloops/example-workflow.yml`, documentation only). Linux, clang and libc++ 18 or newer; it counts loops, not time; link-time optimization flags are removed; tested once, on three projects.
- **Real programs timed whole** (six workloads from four projects picked for their lost loops: LightGBM with three option sets, Draco, tiny-dnn, Spectra): detectably slower for five of the six on EPYC 7763 (1.2% to 7.5% across the two columns, 16 jobs; three of the four projects), four on EPYC 9V74 (3 jobs), three on EPYC 9V45 (5 jobs); the rest were not detectable. Two control programs without lost loops (meshoptimizer, {fmt}) showed no detectable slowdown.
- **Code placement and PGO.** Across 4 placements the reverse loop stays at 5.2x to 8.0x and the forward sum (bounded by `size()`) near 1x; the forward add (bounded by `size()`) swings 0.82x to 1.60x on two models (as compiled 1.58x on EPYC 7763 and 1.60x on 9V74, traced to loop layout, not the check's own instructions), and the verdict leaves out the forward cells that depend on placement. PGO, trained on the timed input, left the cost in most rows.
- **0.99x to 1.09x** for the reverse loop after one added size check before it, with the checks still on.
- **GCC differs.** With GCC 14 and libstdc++'s own `_GLIBCXX_ASSERTIONS` (a different library, different checks) at `-O3`, even the forward add loses SIMD and runs 4.9x to 8.5x slower (7 jobs on 3 CPU models; the low end is one job).

## How much to trust it

- **Shared machines.** GitHub picks each job's CPU. The kernel pool is 95 jobs in 15 runs (23 to 29 jobs for each AMD model, 7 for each of the two main Xeon models, 1 for a third Xeon model); 65 of them come from twelve later runs. Ten of those runs dispatched 100 jobs and 45 returned results: all 100 finished their timing step, and the other 55 were cancelled at the 22-minute limit during the whole-repository check the workflow then ran, before the upload, and returned nothing (the workflow now uploads first). The cut fell unevenly by CPU model (EPYC 7763: 1 of the 45 that returned, against 19 of the first 30 jobs), and the effect of that mix on the ratios was not tested. Two more runs, dispatched with the limit raised to 45 minutes to check that jobs return (not chosen on their results), returned 20 of 20 jobs, 9 of them on EPYC 7763; every one ran past 22 minutes, which supports the account that the old limit, not the timing, cut the others.
- **Mostly x86-64.** Every figure outside the Arm bullet is x86-64 (AMD and Intel). The Arm column is one core type (Neoverse-N2) on shared machines, 30 jobs in 3 runs, clang 18 only; its verdict is INCONCLUSIVE (a borderline one, see the Arm bullet above), and nothing is said about Apple silicon, AWS Graviton or other Arm cores.
- **Mostly one toolchain.** Ubuntu clang 18, libc++, `-O2`, FAST mode. Clang and libc++ 19 to 21, timed on the eight loops (one CPU model with enough jobs), still lose the reverse and stride-2 loops; matrix multiply keeps SIMD there but is not free (1.6x at L1 on EPYC 7763, as slow as a build with no vectorization at all, and 1.15x at L2). A compile-only sweep (`ce-sweep/`, nothing timed) finds matrix multiply lost on clang 16 to 18 at baseline x86-64, kept on 19 to 22 (Ubuntu's own clang 20.1.2 and libc++ 20 agree), and lost again on clang 23.1 and trunk (as served on 2026-10-12). The change is in the compiler, not the library, and clang 19 to 21 price each of the two checks at 1 cost unit where clang 18 prices them at 14 (observed on Compiler Explorer's builds, not the timed ones); that LLVM commit `b6a8f5486b` caused it is inferred, not tested ([study](investigate/vectorizer/matmul/README.md)).
- **Machine state.** Over 10 jobs, steal was 0%, and reported CPU frequency drifted at most 0.57%. The driver was seen on the timed core's hyperthread sibling in 8 jobs.
- **Sizes.** The 2.8x to 8.0x is for the study's sizes. On EPYC 7763 the matrix-multiply sweep gives, as compiled, 2.5x at d = 12, 3.2x at d = 36 (the study's L1 size) and 4.2x at d = 76 (past its 32 KiB L1d), so 2.8x is not a floor for these loops. The range covers both columns: as compiled the in-cache cells of these loops range from 2.8x to 7.7x, with the loops aligned from 2.9x to 8.0x (the lowest is the EPYC 9V45 stride-2 loop at L1 as compiled, 2.81x; the highest the EPYC 7763 reverse loop at L1 aligned, 8.01x).
- **Counts are not time.** The 593 and 4,968 are loops, not hotness.
- **Real programs** (four projects) were picked because they contain lost loops, not sampled.
- **Rules were loosened after seeing results.** The day-one test (the first two runs) judged forward loops by a rule that both runs failed, so the result was no-go as written; the rule was then relaxed in `harness/criteria.json`. The later versions (v2, v3) changed no threshold but added rules (the aligned column, the layout A/A, placement-sensitive cells, pooling per CPU model, 40 repetitions per side) after earlier results were known, so they are not pre-registered. The rule files, plans and expectations were committed in the author's unpublished development history before the runs they govern, except the Arm plan (committed after its runs were dispatched), the holdout plan (2 seconds after the first recorded job start) and the replication plan (see the replication section below). The public history begins on 14 October 2026, after the runs of `s1` to `s4`, the holdout and the rewrite, so for those that order cannot be checked from public records; the records of `s6`, `s7` and `s9` name public commits that hold the rule file as it is now. The hashes stored in the result files show that the rule files did not change after the runs. All versions are kept.
- **What MAP and INCONCLUSIVE cover.** Each word is a statement about the forward in-cache cells (loops bounded by `size()`) left after one exemption that the rule file `harness/criteria-v3.json` sets (it was fixed before the first pooled run, in the author's unpublished development history, though after the earlier runs were known): a cell is left out when the hot loops of the two builds sit differently in memory and the ratio between its as-compiled and aligned results has an interval that excludes 1. The rule has no minimum size for that difference and does not ask whether the cost goes away when the loops are aligned; aligning to 64 bytes removes one source of placement variation, not all of it (the stencil at L1 on EPYC 7763 is 1.006x as compiled and 1.056x aligned). The second test (the hot loop's start within its 64-byte window, its size in bytes, the number of 64-byte windows it spans, and whether it needs an extra one) only rules out pairs that are alike in all four, such as the forward sum's: the first test flags 17 cells in the x86-64 and Arm pools and the second removes none of them, because the hot loop's start within its window differs between the two builds in all 17. For the forward add the two x86-64 builds' hot loops also differ in size (56 and 31 bytes), so "placement-sensitive" there covers the loops' layout and their code together, and aligning removes the layout part only; the cause was examined on EPYC 7763, EPYC 9V74 and EPYC 9V45 only (`investigate/FINDINGS.md` records FAST choosing interleave count 1 where NONE chooses 2), so for the Intel and Arm cells, and for the stencil on every model, the test shows that the layouts differ, not why. On Arm the matmul pair has the same size (36 bytes) and differs in start offset, windows spanned and extra window. The exemption left out 3 of the 6 forward cells on each AMD model, 2 on the Xeon 6973P-C and 1 on the Xeon 8573C, each listed with its ratios in the model's verdict line in `results/s7-pooled/pooled.json`. On each AMD model the 3 judged cells are the forward sum at L1 and L2, which compiles to identical machine code in both builds (the same in all 95 jobs, so it measures noise, not the check), and the stencil at L2. The Xeon 6973P-C's forward add at L1 (1.23x as compiled, 1.20x aligned) is among the cells left out, and the Xeon 8573C's (1.06x in both columns) is judged, so the two Intel words do not rank those models by cost. The rule asks whether the two columns differ, not by how much: the 6973P-C's forward add at L1 is left out with a ratio of 1.027 [1.021, 1.035] between its two columns (7 jobs), although it costs 1.199 even when aligned; of the 17 cells left out in the x86-64 and Arm pools, 4 are above 1.02 in the aligned column by the point ratio (the 6973P-C's forward add at L1, the EPYC 7763's stencil at L1, the Xeon 8370C's forward add at L1 from its 1 job, and the Arm core's matmul at L1) and 5 by the upper end of the interval, the fifth being the EPYC 9V45's stencil at L1 (1.0204). The 6973P-C's MAP and the Arm INCONCLUSIVE each rest on one cell within 0.002 of the 1.02 limit (1.018 and 1.021); those are the stored seed's ends: re-drawn under other seeds the 6973P-C's whole analysis is INCONCLUSIVE in 13 of 60 and 3-job subsets of its own jobs are INCONCLUSIVE in 27 of 30 ([calibration](robustness/README-calibration.md)), and an identical binary timed at L2 is about as wide as the intervals of the cells the two words rest on (2.34% pooled on the 6973P-C and 2.62% on the Arm core, against the 2% ceiling the rule reads at L1; see "Floors, sizes and builds"), so a word that close is better read as undecided at this sampling. A sensitivity, not a verdict ([robustness/README-placement-floor.md](robustness/README-placement-floor.md)): if the exemption also required the ratio between a cell's as-compiled and aligned results to be at least 2% away from 1, four pool-and-model rows would change from MAP to INCONCLUSIVE. The four are the EPYC 9V45 in each of the pools `s4`, `s6` and `s7`, on the stencil at L1, and the Xeon 8573C in the x86-64 replication set `s9-x86-c`, on the forward add at L1. The page's x86-64 verdict words come from `s7`, so the EPYC 9V45 row of that pool is one of the four, and the page's replication figure shows `s9-x86-c`, which holds the fourth. With each row's own layout A/A half-width as that minimum instead no row would change. The larger of the two minimums changes the same four rows; the stored words are unchanged, and the note does not say which rule is right.
- **Floors, sizes and builds.** The A/A control behind the forward limit is the forward add at L1. The same A/A at L2 is timed in every job (stored as `aa_extra` in each job's `details.json`) and pooled per CPU model in `robustness/aa-l2.json` (table in the [details](readme-parts/DETAILS.md)): its pooled half-width is at most 0.38% on four x86-64 models, 2.34% on the Xeon 6973P-C (0.54% at L1) and 2.62% on the Arm core (0.009% at L1), the last two above the 2% ceiling; on the Arm core that A/A is as wide as the cells it would judge (above). Read at L2, the ceiling clause would turn the 6973P-C's MAP into INCONCLUSIVE and change no other stored word in the four pools that file covers; the rule reads L1 only and is not changed. For the real programs the A/A of an identical binary is at most 0.37% on EPYC 7763, while building the same program without checks at `-falign-loops=64` moves it by 2.3% for {fmt} on EPYC 7763 and by 6.3% for Spectra on EPYC 9V45, so a program effect smaller than that is not separated from code placement. RAM-sized working sets were timed in 13 early jobs only: there reverse took 1.1x to 2.9x and stride-2 1.1x to 1.9x, far less than in cache, and they were not re-timed in the pooled runs, so the 2.8x to 8.0x is for data that fits in the cache. The programs were built without `-DNDEBUG`, so their own `assert` checks are active in both builds; release builds differ and the size of that difference was not tested.
- **Independence and holdout.** On the 95-job pool a block bootstrap and the other interval methods tried (exploratory, [report](robustness/report.md)) change no verdict form on EPYC 7763, 9V74, 9V45 or the Xeon 8573C; the Xeon 6973P-C stays MAP under seven of the eight, and changes with the set of jobs more than with the method (leaving one job out, in turn, gives INCONCLUSIVE in 6 of its 7 cases). A fresh run, planned in writing (the records do not show the order), matched the original 30-job pool on EPYC 7763 and 9V74, not 9V45. Run to run, a run's point fell outside another run's interval on EPYC 7763 in 168 of 640 comparisons (26%; 17% in the 75-job pool), against 148.4 expected if the intervals were exactly calibrated; the excess lies in the reverse, stride-2 and matrix-multiply cells (104 of 240, against 61.7 expected), not in the forward ones (42 of 240, against 53.8), and on EPYC 9V74 the count is 62 of 384 against 88.4 expected ([calibration baseline](robustness/README-calibration.md)).

## Replication and the matrix-multiply sweep

Two verdicts rested on a thin margin, so two replication sets were planned in [replication/PLAN.md](replication/PLAN.md) (the plan's commit time in the author's unpublished development history is 27 seconds before the first job's recorded start, and the harness started 25 and 29 seconds after dispatch in the two Arm runs of Oct 16 that did not queue, so that margin lies inside the lag and the order of plan and dispatch cannot be established from the records; no public record shows it, and the plan's hash in `replication/results.json` is computed when the comparison is built, so it shows the file is unchanged, not when it was written): set B, 30 more Arm jobs in 3 runs (29 on Neoverse-N2 and 1 on a Neoverse-V3 core, which has no verdict), and set C, 40 more x86-64 jobs in 4 runs, both dispatched from the default branch at commit 32ab03c. Each set is pooled alone, with the same code and the unchanged rules, and reported beside the pool it replicates; the verdicts and numbers above stay as they were. The pooled forms of the earlier jobs with the new ones are secondary, because the sets were requested after a borderline reading. Two of the four set-C combine jobs ended red on `harness/pool_check.py`, on a model with fewer than 3 jobs (one job in one run, two in the other); the checker now samples only models with 3 or more jobs (the minimum for a verdict), no verdict uses a model with fewer, and the pooled files and the rules are unchanged: only that check's sampling rule changed.

- **Arm.** Set B alone (29 Neoverse-N2 jobs) is INCONCLUSIVE again, on the same cell: the forward add at L2, aligned, ends at 1.0211 in set A and 1.0247 in set B against the 1.02 limit, with a point estimate below 1 in both (0.986 and 0.995). The cell sits close to the 1.02 limit in both sets, so a second INCONCLUSIVE is a weak repeat of the word and not strong evidence for it. Sets A and B pooled (59 Neoverse-N2 jobs) give MAP, with that end at 1.0150; the harness labels that form unstable, because each of the six runs alone is INCONCLUSIVE. The stored Arm verdict stays INCONCLUSIVE.
- **x86-64.** Four models had 3 or more jobs in set C. Two gave the same verdict word as the 95-job pool (EPYC 7763 and 9V74, MAP) and two a different one. On EPYC 9V45 (23 jobs MAP, then 5 jobs INCONCLUSIVE) the stencil at L1 is left out as placement-sensitive in the 95-job pool and judged in set C; its aligned upper end is 1.0204 and 1.0202 against the 1.02 limit. On the Xeon 8573C (7 jobs INCONCLUSIVE, then 7 jobs MAP) the forward add at L1 is judged in the 95-job pool and left out in set C; it costs 1.058 and 1.060 aligned. In both, the word changed because the written rule treated one cell differently, while the measured cost of the cell is about the same. The 8573C's MAP in set C is not the cost going away: the exempt forward add still costs 1.054 as compiled and 1.060 aligned.
- **Not tested.** Set C drew 1 job of the Xeon 6973P-C (3 are the minimum), so the question of its borderline MAP has no answer from these sets. Pooled with its 7 earlier jobs (8 jobs, a secondary form) it is INCONCLUSIVE, because the stencil at L1, left out as placement-sensitive in the 7-job pool, is judged and ends at 1.0216; one added job does not settle which word is right.
- **Reproduction and the headline.** 26 of 32 Arm points and 101 of 128 x86-64 points lie inside the earlier pool's interval, counting the as-compiled and the aligned column (aligned alone: 11 of 16 and 48 of 64, the form the plan asked for; the both-column count was chosen after the data were in); 30 of 32 and 122 of 128 differ from the earlier point by under 1%, and the largest differences are 3.74% (Arm stride-2 at L2, aligned) and 2.14% (Xeon 8573C stride-2 at L2, as compiled). The inside test is strict where the earlier interval is very narrow (a half-width under 0.1% of the ratio for 18 of the 32 Arm points and 24 of the 128 x86-64 points); the farthest missed point is 0.67% (Arm) and 0.73% (x86-64) from the interval. The count is descriptive: a new pooled point carries its own noise, so fewer than 95% of points are expected inside even when nothing has changed. For reverse, stride-2 and matrix multiply in cache, set C ranges from 2.805x to 7.993x over the four models with 3 or more jobs, so the printed 2.8x to 8.0x stands; one cell, the EPYC 9V45 stride-2 at L1 as compiled (5 jobs, 2.8053x), lies 0.0003x under the stored minimum of 2.8055x and prints as 2.8x.

The Arm matrix-multiply cost (1.55x at L1 with the NEON loop kept) rested on a reading of the listing. [dsweep/PLAN.md](dsweep/PLAN.md) fixed a test before any run. It was drafted before the sweep code, revised while the code was written and once more after a review that changed the deciding statistic, and committed alone, before the code commit and the first run, in the author's unpublished development history; its hash, stored in every result file, shows that it did not change after the runs. That order cannot be checked from public records; what the public repository holds is the plan file, byte for byte the one here, in commit f7f7d48 on the temporary public branch `dsweep-smoke`, dated 08:44 UTC, about 9 minutes before the first job's recorded start (08:52 UTC) and together with the code, so whether the plan was written before the code is not observable there. The test: is the time FAST adds per inner call a fixed cost (H1), proportional to the matrix size (H2), or smaller at larger sizes ("falls")? Three runs (18 jobs: 6 on Arm in one run, 12 on x86-64 in two) timed matrix multiply at 15 to 17 sizes for each CPU model.

- **Registered words.** EPYC 7763 (9 jobs, 2 runs): H2, a cost per element, which the plan expected where the loop loses SIMD. Neoverse-N2 (6 jobs, 1 run): "neither", because the two columns disagree: as compiled the excess "falls" (fixed share 1.332), aligned it is H1 (1.090). Both shares are above 1, so it is not a mixture. EPYC 9V45 (2 jobs) and Xeon 8573C (1 job) were too few for a word. The plan's illustrative table gave R(12) = 3.35 under H1 and 2.31 was observed, so the table's size did not hold; the rule decides, not the table.
- **What the numbers show without the word.** On Arm H2 is rejected in both columns. FAST adds 77 extra instructions per inner call (77.0 to 77.2) at every size with d = 4 mod 8 from 12 to 148 (instruction counts, a secondary column, not times). As compiled, the excess time per inner call is 4.9 ns at d = 12, 3.8 to 4.0 ns at d = 28, 36, 44, 52, 76 and 108, 2.8 ns at d = 148 and 0.46 ns at d = 209; aligned, 4.7 ns, 4.2 to 4.3 ns, 3.7 ns and 0.50 ns. The word "falls" as compiled rests on the two smallest sizes, 12 and 20, with the excess flat, at the sizes with d = 4 mod 8, from d = 28 to d = 108, across the L1 boundary of the core (d = 76 and 108 are past its 64 KiB L1d), and smaller again only at d = 148 and d = 209, which are context and not fitted (a reading made after the result, not part of the rule). A setup cost before the NEON loop is consistent with this; the registered word is still "neither", and no further runs will be made.
- **Caveats.** Arm is one run of six near-identical jobs, so its intervals cannot show run-to-run or host-to-host spread; `-falign-loops=64` moves every loop on Arm (16 of the 17 sizes are flagged placement-sensitive), so the aligned column is not a pure placement control; no hardware counters were read. In the residue scan (context, not fitted), d = 48, a multiple of 8, costs 2.63x as compiled against 1.50x and 1.62x at 49 and 47, so the 1.55x belongs to the study size, which is 4 mod 8.

## Forward loops with a variable bound

The forward loops timed elsewhere in this study (the forward sum, the forward add and the stencil) are bounded by the container's own length, `size()` (the stencil's by `size()` less one). [forwardt/](forwardt/README.md) times six forward loops with clang 18.1.3 and libc++ 18: two controls bounded by `size()` and four loops bounded by a variable `n` (`t02_sum_n`, `t04_scale_n`, `t05_fill_n`, `t06_offset`). Its plan, [forwardt/PLAN.md](forwardt/PLAN.md), fixes the predictions (named P0 to P6) and the rules that turn the ratios into sentences. The plan is the only file of its commit in the public history; that its commit came before the code and the runs rests on the author's clock and on that history, and is not otherwise checkable. The plan's sha256 is stored in every result file, and `scripts/check.py` compares it with the file.

Three measurement runs (18 of 18 jobs returned) drew EPYC 7763 for 7, EPYC 9V45 for 2, EPYC 9V74 for 3 and Neoverse-N2 for 6 jobs. A CPU model is read only with 3 or more jobs, so EPYC 9V45 is not read. Prediction P1 held on both x86-64 models: the two controls, `t01_sum_size` and `t03_scale_size`, which are bounded by `size()`, stayed inside their bands. On the two x86-64 models read (EPYC 7763 and EPYC 9V74) the prediction for the sum with a variable bound failed: `t02_sum_n` was predicted at 0.97 to 1.35 times the unchecked time, and its 8 cells (two sizes and two columns on each model) ran 1.985 to 2.043 times, each interval wholly above 1.35. The plan's outcome for the x86-64 models is letter D: the prediction for the sum (P2) failed above its band, so the plan states no limit and no forward-range word for the sum cells, and they are reported as measured. P3 held: at L1 the intervals of `t05_fill_n` and `t06_offset` lie above 1.5 in both columns on both models. For a write cell the plan allows the words "at or above 1.5x" and no other limit. The two columns of `t05_fill_n` differ: on EPYC 7763 at L1 it is 7.790 (7.785 to 7.795) as compiled and 3.970 (3.914 to 4.042) aligned, and the plan's placement statistic (the as-compiled ratio over the aligned one) is 1.962 (1.926 to 1.990). A single cost for that loop is not read from the two columns. The other predictions on these models (P0, P2n, P4 and P5) held.

Neoverse-N2 is one run of six jobs, so its intervals cannot show spread between runs. Prediction P1, for the two controls, held on the 4 of 8 combinations of loop, size and column that were decidable; 4 were not. `t02_sum_n` is lost on this core: 5.854 (5.852 to 5.855) as compiled and 5.829 (5.755 to 5.839) aligned at L1. The plan gives it no band here, so the numbers are reported without one. Prediction P6, for the writes, failed on one cell: `t05_fill_n` at L1 as compiled is 0.883 (0.880 to 0.886), wholly below the lower edge 0.95, and aligned it is 1.022 (1.019 to 1.024), inside the band; the two columns of that loop differ. At L2 the aligned cell of `t05_fill_n` is 0.949 (0.947 to 0.952), whose interval contains the lower edge 0.95, so it is neither inside nor outside the band; the two `t06_offset` cells at L2 are not decidable (A/A half-width 5.98 %), so 6 of the 8 combinations of P6 are judged.

These are results for six hand-written loops with clang 18.1.3 and libc++ 18 at `-O2`. The sentences elsewhere that say forward loops cost little or keep SIMD are about loops bounded by `size()`; they are not a result for forward loops with another bound. The loop census (`corpus/README.md`, clang 18) counts 444 lost loops, one per function a loop was compiled into; 228 of them, at 38 source locations, fall in its class "forward loop bounded by a variable", assigned by a text pattern on the loop header and body. The census does not know how often any of them runs, and how many of the 228 have one of the six shapes timed here is not counted. The ratios above are for six hand-written loops: they are not a cost for those 228 loops and not a share of a program's run time.

Every cell of the six loops is in [forwardt/README.md](forwardt/README.md), and the decidable aligned cells of the four variable-bound loops are listed in the [details](readme-parts/DETAILS.md).

## Details of the check and the rerun

The page check needs `pip install playwright` and `playwright install chromium` (`--with-deps` on Linux), and network access to fonts.googleapis.com and fonts.gstatic.com, where the page loads its fonts from; without that access it answers those requests itself and runs on the system fonts; on the Windows system fonts it was tried with, every check passes except the two (`FONT_DEPENDENT_CHECKS` in `scripts/check_site.py`) that measure the hero's first view against the web fonts, so the run then fails instead of ending `ALL CHECKS PASSED` (other systems' fonts were not tried). Without the playwright package that step is skipped and the run ends `CHECKS PASSED, WITH SKIPPED STEPS` with exit code 3, not `ALL CHECKS PASSED`. To view the page from your clone instead of the live one: `python -m http.server 8000 --directory site`, then open http://localhost:8000.

Of the stored runs, those that ran to the end took, from dispatch to finish and queueing included: 44 to 45 minutes for the 2 x86-64 runs of `s7` (10 jobs each; their `measure.yml` still ran the whole-repository check inside every job), 32 to 42 minutes for the 4 x86-64 runs of `s9` (10 jobs each; the workflow without the whole-repository check; two of the four ended red in the combine step, after every measurement job had finished, see the set-C paragraph above), 12 to 23 minutes for the 3 Arm runs of `s8` and 33 minutes for the 3 Arm runs of `s9`. A job is cancelled after 45 minutes (`timeout-minutes` in `measure.yml`; the earlier 22-minute limit cut off the ten `s6` runs about 28 minutes after dispatch). The durations come from the Actions run list, read on 29 October 2026 and kept in `tests/data/run_durations.json`. The early runs (`s1` to `s4`, including the original 30-job pool) ran on 2-vCPU runners and every later run, a rerun today, on 4 vCPUs; the harness pins one vCPU, so the difference is not expected to matter, which was not tested. Compiler versions are recorded in the result files, not pinned (clang 18.1.3 from Ubuntu's archive; `versions/install.sh` takes whatever clang 19 to 21 apt.llvm.org then serves). The workflows pin the GitHub actions they use to a commit in `ci.yml`, `dsweep.yml`, `forwardt.yml`, `measure.yml`, `pages.yml` and `siblings.yml`; the runs under `results/` ran before the pins and used the moving `v4` tags of `actions/checkout`, `actions/upload-artifact` and `actions/download-artifact`, and the other 10 workflows still do.
