1Result, in full

Four words used below. A run is one start of the measuring workflow on GitHub. Each run starts machines at once, and each machine’s share of the work is a job; GitHub decides which CPU model each job gets. The pooled ratio of a CPU model combines every job that drew it, in all runs: the geometric mean of the jobs’ own ratios. Its interval comes from resampling whole jobs and then the repetitions inside each job, so it includes the spread between machines, not only the noise inside one. A CPU model needs at least jobs to be judged.

Each part of the page uses its own set of jobs, so the same loop can show slightly different ranges in different places. Figures 1 and 3, Tables 1 and 2 and Appendix A: the pooled runs ( jobs), sizes L1 and L2, the column named (aligned or as compiled). Figure 2’s footnote: the L1 size only. Section 5: the jobs of the rewrite runs, aligned. Section 6: the jobs of the toolchain runs, aligned, including CPU models drawn too rarely to judge here. 2Why uneven, in full

SIMD (single instruction, multiple data) is the processor’s way of working on several array elements with one instruction: on the baseline x86-64 these binaries target, one xmm register holds four 32-bit integers, so paddd adds four pairs at once. A compiler turns a loop into SIMD code only when it can prove the transformation is safe, and the bounds check makes that proof harder, because the check can stop the loop at any element.

1 Turning vectorization off by hand, with no checks (-fno-vectorize, the NOVEC build), makes the reverse loop times as long on (L1 size, as compiled, pooled); the check makes it times as long on the same jobs and size. Losing SIMD is the only factor measured; it accounts for about a third (%) of the extra time. The rest, %, is not explained by this measurement; it presumably comes from the compare and jump on every element in a loop that is no longer unrolled (inferred, not measured).

3The control that caught us, in full

One forward loop, c[i] = a[i] + b[i], looked expensive on some CPUs: as compiled, it ran up to times as long with checks on, although it stays vectorized in both builds. The check’s own instructions were not the cause; the loop layout it induces was. With the checks on, clang emits a shorter SIMD loop that handles numbers per pass instead of ( bytes, starting at address ). As placed, that loop is the slow one on these AMD cores; aligned, it runs faster than the unchecked one. Both builds’ hot loops cross a 64-byte boundary, so the crossing alone does not tell them apart; the hardware reason (presumably how the processor fetches small loops in 64-byte windows) is inferred, since the investigation had timings only, no hardware counters.

Rebuilding both binaries with every hot loop aligned to 64 bytes (-falign-loops=64) removes the effect. That is why every figure offers the aligned build, and why the rules now call a forward loop placement-sensitive when two things hold: the pooled ratio of its two columns (as compiled ÷ aligned) has an interval that excludes 1, and its hot loop sits differently against the 64-byte windows in the two builds. Such a loop is shown and flagged but not used to judge the forward side. The full write-up is in the investigation’s notes.

Counted, not timed. This section counts loops in source code that clang compiles; it times nothing. How often a loop runs (its hotness) cannot be known when compiling, so these counts make no claim about runtime cost, and none about Google’s average.

Each project was compiled twice with , checks off and on, and the compiler’s own optimization records say which loops it vectorized. A loop is lost when it is vectorized with the checks off and not with them on, the kind that Figure 1 shows paying several times. Census 1 took general libraries (parsers, JSON, compression, logging). Census 2 took projects of numeric, physics, graphics, machine-learning and compression code (including Stockfish and EnTT), where such loops are likely to live; its list and rules were committed in its plan before the first compile.

Every lost loop of census 2 is in the projects’ own code, and for of ( of locations) a separate rebuild traced a libc++ check to a line inside the loop.       8Method, in full

      The rule history, in short:

        What the loops index
        Each test loop checks every operator[] access. Compile-only variants (clang 18, no timing): two equal-size vectors still lose SIMD; a reverse loop over one vector loses its check entirely; iterators are unchecked in libc++ 18. Details.
        Timing
        repetitions per side in alternating order (ABBA), fixed in advance, pinned to one CPU, timed inside the binary. A job’s ratio is the median with checks over the median without.
        A/A
        The unchecked binary against a byte-identical copy of itself, pooled the same way. Pooled per CPU model it came out at % to % half-width, against a ceiling of %.
        Controls
        Forward loops vectorized in both builds (expected near 1×); loops that lose vectorization, with a NOVEC build as a yardstick; and a layout A/A, the unchecked binary rebuilt at a different loop alignment.
        Instructions
        Cachegrind counts the instructions each build executes, at both sizes, beside every time ratio: instructions, not time. No rule reads them.
        Verdict
        Computed by script per CPU model from the written pass rules; nobody edits the result by hand. Every number on this page is read from the data files the runs produced.
        Builds
        Every loop is compiled with on and , once with _LIBCPP_HARDENING_MODE_NONE (checks off) and once with _LIBCPP_HARDENING_MODE_FAST (checks on). FAST is libc++’s cheapest hardening mode; among other things it checks operator[] and stops the program with a trap instruction, ud2, on an index out of range. A second pair adds -falign-loops=64.
        Pooling
        All jobs of runs, grouped by CPU model; the pooled ratio is the geometric mean of the jobs’ ratios, and its 95% interval a two-level bootstrap with resamples (jobs, then repetitions inside each job) and fixed random streams, so anyone can recompute it exactly. No job is left out for being noisy; a noisy job widens the interval.
        Layout A/A
        The unchecked binary against itself rebuilt at a different loop alignment: what placement alone can do, per loop.
        Negative control
        The forward loops, vectorized in both builds, where the expected cost is near 1×.
        Positive control
        The reverse, stride-2 and matrix-multiply loops, which lose vectorization under FAST (the compiler’s remarks and the assembly), plus the NOVEC build (no checks, vectorization off) as a yardstick of what losing SIMD costs on its own.
        Run to run
        On , the only model with enough jobs in more than one run, a run’s pooled ratio fell outside another run’s pooled interval in of comparisons.
        Tuned until it passed?
