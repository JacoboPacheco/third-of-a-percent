# Versions: does the loop-shape finding hold on libc++ / clang 19, 20 and 21, or only on 18?

Written Tue Oct 13 2026 (time in the commit message), BEFORE any run. No timing number from any newer toolchain exists when this is committed.

## Question
Every timed number in this project is clang 18 with Ubuntu's libc++-18-dev (`gaps/GAPS-2.md`, gap 13). The finding is "loops that lose SIMD under libc++ FAST cost 2.8 to 8.0x in cache; forward loops stay near 1x". That could be a fact about libc++ 18 and clang 18 only: the standard library's hardening and the compiler's vectorizer both changed after 18. This column times the same eight kernels on newer toolchains and publishes whatever comes out.

## What changed after 18 (external reading, labelled; none of it is measured here)
Read Tue Oct 13 2026 with WebFetch; each page was summarised by a small model, not read in full by a person, so a claim here is a pointer to check, not a verified quote.
- Selecting a mode: `-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_{NONE,FAST,EXTENSIVE,DEBUG}`, defined before any header; the page says the numeric values of the macros are unspecified. FAST enables the `valid-element-access` and `valid-input-range` categories, default semantic `quick-enforce` (trap). Loaded: https://libcxx.llvm.org/Hardening.html (no version history on that page).
- 19: bounded iterators for `string` and `vector` as an ABI option (`_LIBCPP_ABI_BOUNDED_ITERATORS_IN_STRING`, `..._IN_VECTOR`), checked only at FAST or above; `_LIBCPP_ENABLE_ASSERTIONS` deprecated (still enables EXTENSIVE with a warning), `LIBCXX_ENABLE_ASSERTIONS` is an error. Loaded: https://releases.llvm.org/19.1.0/projects/libcxx/docs/ReleaseNotes.html (the page's heading says "19.0.0 (in progress)").
- 20: `_LIBCPP_ENABLE_ASSERTIONS` and `LIBCXX_ENABLE_ASSERTIONS` removed; hardening added for `forward_list` and `bitset`; new ABI options `_LIBCPP_ABI_BOUNDED_UNIQUE_PTR` and `_LIBCPP_ABI_BOUNDED_ITERATORS_IN_STD_ARRAY`. Loaded: https://releases.llvm.org/20.1.0/projects/libcxx/docs/ReleaseNotes.html
- 21: hardening assertion semantics (`ignore`, `observe`, `quick-enforce`, `enforce`), marked experimental. Loaded: https://releases.llvm.org/21.1.0/projects/libcxx/docs/ReleaseNotes.html
- Not found in any of these pages: any change to what FAST checks in `vector::operator[]`, and anything about vectorization. So a changed ratio below could come from the standard library, from clang's vectorizer, or from both; this column cannot separate them. (Compile-only data from other clang versions is in `ce-sweep/`.)
- The macro the harness uses (`harness/run.py`, `FLAGS`) is the documented one, so no flag changes. Each job also runs a probe (a `std::vector` index out of range, built NONE and FAST) and records whether FAST traps; if FAST does not trap on a toolchain, that toolchain's rows are INCONCLUSIVE (the macro did not do what the harness assumes).
- Packages: https://apt.llvm.org/noble/dists/ lists `llvm-toolchain-noble-19`, `-20` and `-21` (loaded). https://apt.llvm.org/ (loaded) shows source lines only for 21 and 22 on its front page, and names `libc++-21-dev` and `libc++abi-21-dev`, key https://apt.llvm.org/llvm-snapshot.gpg.key. Ubuntu's own noble archive also has `libc++-19-dev` 1:19.1.1-1ubuntu1~24.04.2 (https://packages.ubuntu.com, loaded). That the `Packages` files of the 19/20/21 repositories hold clang-N, libc++-N-dev and libc++abi-N-dev was NOT confirmed (the index did not parse through WebFetch); the first run confirms it, and every job logs the installed package versions.

## What is built
- `harness/run.py` is run unchanged, with `HARNESS_CXX=clang++-<N>`: the same eight kernels (`kernels/`, unchanged), `-O2 -std=c++20 -stdlib=libc++`, NONE and FAST, plus the aligned pair (`-falign-loops=64`), the byte-identical A/A, the layout A/A, NOVEC, Cachegrind, sizes L1 and L2, `--criteria harness/criteria-v3.json`, no programs, 40 processes per side, ABBA, `taskset` pinned (all of that is the harness; `versions/run_version.py` only sets the compiler, calls it and records the toolchain, the macro probe and the vectorization remarks).
- Matrix: one job set per version N in the input list (default 19,20,21), 10 jobs each, ubuntu-24.04. Artifacts `versions-<N>-<cpu>-j<job>`.
- Pooling: `harness/pool.py`, unchanged, once per version (so per CPU model per toolchain). `versions/analyze.py` reads the pooled files and `results/s4-pooled/pooled.json` (clang 18) and prints, per toolchain and CPU model, the FAST/NONE ratio per kernel and size with the pooled interval, the class from clang's loop-vectorize remark (kept / lost / off-axis, as in the harness), the vectorization width in NONE and FAST, and the ratio against clang 18 on the same CPU model.
- Not a perfect like-for-like with 18: the 18 data are Ubuntu's libc++-18 (1:18.1.3); the newer ones come from apt.llvm.org. Different distributor builds of libc++ are a possible confound and are named as such.

## Rules (fixed now, before any run)
By reference, not copied and not edited: the forward rule, the lost-loop rule, the A/A limit, the minimum of 3 jobs, the pooling and the checksum and build controls are those of `harness/criteria-v3.json` (`verdict.forward_point_max_ratio`, `verdict.forward_ci_hi_limit`, `verdict.lost_ci_lo_min_ratio` = 1.5, `verdict.aa_half_width_max_pct`, `v3.pooling`). `versions/criteria.json` stores only what is new here (below) plus the sha256 of `criteria-v3.json`, which `versions/check.py` verifies.
- A CPU model on a toolchain is INCONCLUSIVE when the pooled verdict of `harness/pool.py` is inconclusive (too few jobs, pooled A/A above 2 %, checksum or build control failed, positive control not seen), or the macro probe shows FAST does not trap on that toolchain.
- A kernel HOLDS on a toolchain and CPU model when its class (from the remarks) is `lost` and, at both L1 and L2, the pooled `ci95_lo` is at least 1.5 in both the as-compiled and the aligned column. The kernels judged are the three that lose vectorization and cost under FAST on clang 18: `k04_rev`, `k05_stride2`, `k08_matmul`. `k06_gather` and `k07_hist` (off-axis) and the forward kernels are reported, not judged.
- THE FINDING GENERALISES on a toolchain and CPU model when all three judged kernels HOLD. It DOES NOT GENERALISE when none of them holds. With one or two it is PARTIAL, and the rows say which. Across the CPU models of a toolchain: the same form on every non-inconclusive CPU model gives that form, otherwise MIXED BY CPU MODEL; no usable CPU model gives INCONCLUSIVE.
- "Does not generalise" is a possible outcome with the same weight as "generalises": for example clang 20 vectorizing the reverse loop with the check kept inside, or a library change that moves the check out of the loop. It would be reported as the headline for that toolchain.
- The forward rule is evaluated and printed for every kept cell (aligned column: point at most 1.02 and `ci95_hi` at most `1 + max(0.02, 2 x pooled A/A half-width)`), as description beside the judged part; it is not part of the three-way form.

## What is published
Whatever comes out, per toolchain, including INCONCLUSIVE and a run where an install failed (named as such, with the log). No toolchain, kernel, CPU model or job is dropped after seeing a number. Rows added by this column (the ratio against clang 18, the passed forward rule, widths) are descriptive: no new rule reads them. Statements about causes (library versus vectorizer) are not made from this data.

## Limits
Three newer versions, the CPU models the runners draw, the same eight kernels, int32 `operator[]` loops, SSE2 baseline, no PGO; no program timings; runners are shared VMs (A/A floor measured per job, as before). The run-to-run reproduction check that `pool.py` makes needs at least two runs per version; one run gives a pooled number without it, and that is said in the report.

## Run
In the public repo: `gh workflow run versions.yml -f versions=19,20,21`, then download the `versions-analysis` artifact (`analysis.json`, `report.txt`, `pooled-<N>.json`). Offline: `python versions/check.py`.
