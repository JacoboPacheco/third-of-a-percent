    Abstract

    Google reported that hardening libc++ (checking every vector[i] against its size) cost its services 0.30% on average (Google Security Blog, Nov 15 2024[1]). Timed with checks off and on, loops that lose SIMD run several times slower; forward loops that keep it cost little on the AMD models when aligned (up to 1.6× as compiled on two, from code placement).

    Scope, census, rewrites, other compilers

    The scope is clang 18.1.3 with libc++ 18.1.3 in FAST mode, -O2, no profile-guided optimization in the main timing.

    • 2.8 to 8.0× as long in cache for loops that lose SIMD (several array elements per instruction) under the check; forward loops that keep SIMD stay near 1× on the AMD models when aligned (one AVX2 exception, 1.11×).
    • 444 of 4,968 vectorized loops in numeric projects lose SIMD (one project, LightGBM, holds about three quarters of them), against 1 of 593 in general libraries; in both counts most of the loops are libc++’s own, and none of those lost SIMD; counted, not timed.
    • 0.99 to 1.09× for the reverse and matrix-multiply loops after small rewrites, checks still on.
    • Other compilers, compiled only: clang always loses the reverse and strided loops, never a forward one; GCC at -O3 usually loses the forward add too, and pays at -O2.

    This neither confirms nor contradicts Google’s average over whole services. Six real-program workloads from four projects (LightGBM three ways, Draco, tiny-dnn, Spectra) timed whole: 1.2 to 7.5% slower with checks on, five of the six detectably on one AMD model (three of the four projects), fewer on two others (see Real programs).

    Limits: what this cannot tell you
    • Your production average: these are single loops, not services.
    • Six real-program workloads (four projects) timed, picked for their lost loops, no profile-guided optimization in the main timing; counts are not time.
    • Timed: one main toolchain (clang 18.1.3, libc++, SSE2), the other setups on few jobs. Compiled only: the 14 compiler versions (28 Compiler Explorer compiler ids) in section 6. Arm: one core type, clang 18 only; no real programs or other compilers were timed there (section 6a).
    • Repetitions that are not independent would narrow the intervals; a block bootstrap on the -job pool leaves the verdict of every CPU model unchanged (robustness report).

    2Why the cost is so uneven

    SIMD does several array elements per instruction. A check inside the loop can stop the compiler from using it.

    SIMD (single instruction, multiple data) handles several array elements with one instruction: on x86-64 one xmm register holds four 32-bit integers, so paddd adds four pairs at once (the Arm core in section 6a uses NEON, Arm’s version of the same idea). A compiler uses it only when it can prove that safe, and the bounds check makes the proof harder, because it can stop the loop at any element.

    The machine-code view of each loop shows both outcomes. Each check is another way out of the loop, and clang vectorized a loop only when it could count the iterations to every exit (observed; that the count is the cause is inferred). In the forward loops it can: the sizes are tested once, before the loop, and the check runs only on the leftover elements. In the reverse loop the check no longer depends on the loop counter, its branch stays inside the loop with no count (could not determine number of loop iterations), so the four-at-a-time loop is replaced by one element per pass plus a compare and a jump to the trap. Pass-level evidence.1

    3A control that changed the reading

    A forward loop looked slow on some CPUs because of where its code landed, not because of the check.

    One forward loop, c[i] = a[i] + b[i], looked expensive on some CPUs: as compiled, up to times as long with checks on, although it stays vectorized in both builds. The check’s own instructions were not the cause; the loop layout it induces was: clang emits a shorter SIMD loop ( numbers per pass instead of ) that is slow as placed on these AMD cores; the hardware reason is inferred.

    Rebuilding both binaries with every hot loop aligned to 64 bytes (-falign-loops=64) removes the effect, which is why every figure offers the aligned build and why such a placement-sensitive loop is flagged and not used to judge the forward side.

    5What to change

    One up-front size check (with raw row pointers behind it for matrix multiply) brings the reverse and matrix-multiply loops back to 0.99 to 1.09× with checks still on.

    Can a loop keep the checks and not pay? For the four shapes that pay, rewrites that do the same work were built, checked for vectorization and for the original’s result, timed (aligned, against the original with checks off), and given a safety test: run on an input one element too short, the checked build must still stop the program. Select a shape to see every rewrite tried.

    Fast but silently unsafe. std::transform over rbegin() and rend() runs the reverse loop at times, and its checked build on the short input: libc++ 18’s vector iterators are not checked in FAST mode, so the out-of-range write goes through. It is not in the table below.

    10How can 0.30% be true?

    An average over whole services can sit next to an 8× loop. This study does not show the average is wrong.

    What Google reported. An average cost of 0.30% across its services after hardened libc++ became the default in server-side production (Google Security Blog, Nov 15 2024). The post credits the compiler removing redundant checks and the design of the checks, adds that profile-guided optimization helps, and says the cost stays small without it. It also describes one fix to an unneeded check that moved the figure from 0.35% to 0.30%.

    Why it can sit beside an 8× loop. An average over whole services can sit beside a slow loop if few services spend much time in such loops (an inference, not something this study tested). The post itself says a handful of performance-critical code paths still use explicitly unsafe accesses. In the programs timed here, the loops that lose SIMD hold about 0 to 6% of the instructions, yet where the cost is detectable it was 1.2 to 7.5% on EPYC 7763, the model with the most jobs, and the lost loops’ share of instructions did not predict it. Those programs were picked because they contain such loops, so that range is not an estimate for typical code. The two programs without such loops showed no detectable cost on that model; that is two programs, not a rule.

    What cannot be said. How the 0.30% was computed (CPU time or latency, which services, which time window) is not stated in the post. No Google service was measured here. This study neither confirms nor refutes the average; it shows which loop shapes would push a program above it.

    On an Arm core. The same loops were also timed on an Arm core (section 6a); that adds no measurement of Google’s services.
